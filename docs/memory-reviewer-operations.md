# MemoryReviewer Operations

Status: current system document for the MemoryReviewer lifecycle boundary
Scope: activation, status, review reads, backup and restore, exposure bounds, evaluation evidence, and property traceability for the proposal-only milestone, and the attestation verifier that runs beside it (section 9)

This document describes how a deployment owner and an operator run the MemoryReviewer as it exists: a reviewer that stages proposals, plus a Kernel acceptance path that applies one selected proposal at its exact target (section 4, Kernel acceptance). The routed `review.accept` operation calls that path only while the deployment owner's acceptance record admits it (section 2, Acceptance record); no record ships, so `review.accept` changes no memory until the deployment owner writes one. The review switch (section 2, The review switch) is the second way a memory changes: a project whose user tier sets `memory_reviewer.enabled` has its stored memories reviewed and each proposal treated as `memory_reviewer.apply` says, with no record. `docs/host-wire-protocol.md` is the normative wire contract; where this document names a wire field, that document governs.

## 1. What runs and what never runs

The MemoryReviewer worker is one task per data home. Each pass it reads the deployment owner's activation record, and while that record matches the live deployment it claims Ready review jobs of every bound project whose MODULE memories authority the owner recorded, except reviews of stored memories, which the review switch runs (section 2), runs each through the shared coordinator, and settles it: a staged proposal selected by a completed receipt, or a content-free abstention, or an unknown outcome. Every disclosure of a review job to the remote model goes through the Kernel's egress policy and the Memory Store's committed attempt marker first; nothing is sent without both. A session review under `memory_reviewer.review: session` sends through the Kernel's egress verdict and the bounded attempts section 2 describes, with no attempt marker.

Two producers feed the queue. The History Summarizer reserves a job for each accepted fact set before it publishes the chunk, and activates the job as part of that publication; the Memory Classifier enqueues bounded selection pages of canonical memories. Both paths are exercised by real-store tests named in section 8.

Under the owner's activation record, a proposal changes a canonical memory only through an explicit `review.accept` under the owner's acceptance record, and a default-`Sensitive` subject, which every History Summarizer subject is, stays local: the run abstains by policy before any request and records that abstention.

A project whose user tier sets `memory_reviewer.enabled` runs without either record. The worker selects that project's memories itself, sends each review through the host's model execution to the model the user configured, which reads `Sensitive` text and is refused `Secret` text, and treats each published proposal as `memory_reviewer.apply` says. Under `memory_reviewer.review: session`, the default, the switch reads each session that ended beside the statements the project delivers and writes the changes a later user message makes; under `review: memory`, and under `apply: propose`, it reviews stored memories one by one and treats each proposal as `apply` says. The switch reviews nothing else: the History Summarizer hands a root's fact sets to review only under a memories authority the owner recorded and an open activation record. "The review switch" and "Change detection at a session's end" in section 2 describe it.

## 2. Activation (Q36, Q38)

The gate is closed until the deployment owner writes a runtime identity record at

```
<data home>/memory_reviewer-activation/runtime-identity.json
```

The directory must be mode `0700` and the file mode `0600`, both owned by the daemon's user. A record another user could read is refused, not read. The record is JSON with exactly these fields; an unknown field makes the record malformed.

| Field | Meaning |
| --- | --- |
| `schema` | `1`. |
| `model` | The canonical model id every request names. The provider's reported model is checked against it at response time and a mismatch ends the attempt without releasing text. |
| `prompt_template_version` | The revision of the `extracted_facts` question template compiled into the daemon. |
| `step_schema_version` | The MemoryReviewer step schema version compiled into the daemon. |
| `scanner_ruleset_version` | The redaction detector revision compiled into the daemon. |
| `egress_policy_version` | The MemoryReviewer policy union version compiled into the daemon. |
| `kernel_baseline_digest` | SHA-256 of the Kernel schema baseline compiled into the daemon. |
| `memstore_baseline_digest` | SHA-256 of the Memory Store schema baseline compiled into the daemon. |
| `kernel_incarnation` | The Kernel database incarnation id of this deployment. |
| `memstore_incarnation` | The Memory Store incarnation id of this deployment. |
| `provider` | `<host>/v1/messages@<anthropic-version>`, as the sender identifies the endpoint it dials. |
| `credential` | `ANTHROPIC_API_KEY`: the one startup-envelope credential the sender's protocol writes into its request. Any other name closes the gate as `unknown_credential`, even when the envelope carries it. |
| `credential_fingerprint` | The identity the daemon's committed harness selection, `<data home>/eidnara/harness-closures/active-selection.json`, records under `credential_identities` for that credential: an HMAC keyed under this start's connection key, never the secret itself. The key is fresh at every daemon start, so the value changes at every start. |
| `provider_retention` | `{attested_by, attested_on, retention_terms, finite_work_exposure_acknowledged}`: the owner's statement about the provider account's data retention and an explicit `true` acknowledging that every run spends bounded provider work. |

Every term is compared against the live deployment on every pass and again before every job. Any mismatch closes the gate, and the worker runs nothing and sends nothing. The record therefore has to be rewritten when a binary changes any compiled version or baseline digest the record names (the gate binds those terms, not a build identity, so a binary that changes none of them is admitted by the existing record), when either store is replaced (its incarnation changes), when the provider or endpoint changes, when the secret is rotated, and after every daemon start, because the credential identity is derived under that start's connection key. That is the Q38 rule made mechanical: owner approval of provider retention and finite work exposure precedes the first remote call for exactly the deployment the record's terms describe, and no approval carries over to a deployment they do not name.

The status block reports only the closed kind (`identity_mismatch`), never which term differs. The term and the deployment's live value are written to the daemon's log, `<data home>/.eidnara-coordination/eidnara.log`, once per distinct reason: `daemon: memory_reviewer activation gate closed: activation record names another kernel incarnation; the live value is <id>`. Every identity term is reported this way, so a draft record can be corrected one term at a time from the log. The credential is not: a name the sender does not dial with closes the gate as `unknown_credential`, and a mismatched identity logs only `activation record names another credential`, with no live value. The owner copies the identity from the selection file named above. The compiled versions and digests are not published on any other operator surface. Nothing reads the record except the worker; there is no operator command that writes it, and the daemon never writes one.

The credential is read from the startup envelope's credentials, never from the process environment. The host always hands the daemon its Model Execution supervisor and the envelope's credentials; a record naming a credential the sender does not dial with closes the gate as `unknown_credential`. Until the daemon has committed its harness selection for this start, no credential identity exists and the gate reports `unreadable`.

### The review switch

`memory_reviewer.enabled` is a user-tier key, off by default; a project-tier value is ignored with a warning, in the daemon's tier merge and in each plugin's project strip. The worker reads it from the user tier at every pass (`ConfigCache::user_tier`, `crates/daemon/src/config.rs`), with five settings (the four below and `memory_reviewer.review`), so a change to any of them takes effect at the next pass (a newly named classifier decides once a session that bound after the change asks for work, as "Stage 1 by a typed classifier" says), also for a root that closed with the switch on (a root that closed with the switch off is listed again at its next bind): `memory_reviewer.model`, the `provider/model` every proposal request names (absent, the first model of the History Summarizer's chain); `memory_reviewer.stage1_model`, the `provider/model` of the small chat model that decides stage 1 of each review (absent, derived from the review model as "Stage 1" below says); `memory_reviewer.apply` (`propose`, `contest`, or `apply`; `contest` when absent); and `memory_reviewer.classifier`, the `provider/model` of a typed classifier that decides stage 1 in the small chat model's place while a harness answers its work (absent, the small chat model decides). A model key takes a literal `provider/model`; a value outside that form, or one holding an `{env:}` or `{file:}` reference, is ignored with a warning. The plugins' config schema carries the same rule as a pattern on the three model keys (`assets/eidnara.schema.json`), so an editor flags such a value and a plugin reports it at load. A plugin's loader leaves a value of those keys that holds a reference unset before it substitutes variables, with a warning that names the key (`screenUserTier`, `packages/opencode-plugin/src/config/fold-authority.ts`), so the plugin and the daemon both read the key as absent; one fixture holds the daemon and the schema to the same verdicts (`packages/opencode-plugin/src/config/__fixtures__/memory-reviewer-model-parity.json`). The daemon alone also ignores a classifier longer than 256 bytes or one that holds a control character; a plugin that reads such a value asks for classifier work and the daemon answers `disabled`. An enabled switch also sets `source_capture.enabled` and `contradiction_candidates.enabled` for the route, because a review reads the message blocks a memory cites and the source text recorded after it. Those two consents are part of the configuration a route loads at its bind, like the keys themselves: a session that was open when the switch was turned off keeps capturing until its route is bound again or closes, and a route bound afterwards captures only under its own keys. A switch with no model to name reviews nothing, and a root whose own configuration file the load refused is reviewed by no one.

The switch stands in for the owner's runtime identity record for its project. The worker's pass over switched projects (`Worker::switched_pass`, `crates/daemon/src/memory_reviewer/worker.rs`) builds the approval from the live deployment: the host route's identity (`host-model-execution/<harness>/<provider>/<model>`), the configured model, the host's credential source, and the live Kernel and Memory Store incarnations. `activation_state` reads `open` while the worker's latest pass found a switched project to review, and the owner's record otherwise, which the worker evaluates on every pass and again before each switched run. The record keeps its own state beside the switch (`MemoryReviewerStatus::recorded_state`, `crates/daemon/src/memory_reviewer/lifecycle.rs`), and that state alone admits fact sets and the scheduler's selections, so the switch opens neither. The route registry records a root's binding when it sets the switch (`RouteBindings::review_roots`, `crates/daemon/src/lib.rs`), so a switched project stays under review after its last route closes, for the life of the process, with the harness and credential fingerprints of its last binding, and a session shorter than the worker's pass interval is reviewed by the next pass. A switch turned off in the user tier ends review at the next pass.

What the switch changes, step by step:

| Step | Under the owner's record | Under the switch |
| --- | --- | --- |
| Transport | the reviewer's own verified connection to Anthropic or Bedrock, with a startup-envelope credential | the host's model execution through the History Summarizer's producer factory (`crates/daemon/src/memory_reviewer/host_execution.rs`): the harness child sends the request under the deployment's credential source, so keys, a profile, and a refreshed token all work; each request runs in a session of its own (`eidnara-memory_reviewer:<digest>`) that is deleted when it ends, also when a cancellation drops the request; the request waits up to 2 s for the deletion and never into the last second before its attempt deadline |
| Model binding | the request names the record's model and the provider's reported model is compared with it | the request names the configured `provider/model` and the host runs that pair. A Pi child reports the model id of its answer; the host carries it in an `answering_model` unit ahead of the text, and the reviewer releases the text only when that id equals the model of the configured pair. An answer that names another model, or a Pi answer that names none, ends the attempt with the `ModelMismatch` refusal and closes review for the rest of the process, as on the direct route. An OpenCode child's transcript carries no model id, so on that harness the dispatch is the binding |
| Destination | `Remote`: `Normal` content with remote-allowed provider egress | `ConfiguredModel`: every stored class a local reader is served short of `Secret`, whatever the provider-egress class; the render check and the secret scanner apply unchanged |

A route has one authority binding, and every domain resolves through it. A root whose route is bound to another identity that holds a preparing, active, or draining authority in any domain, such as an owner's notes authority, keeps that binding, also when that identity binds the route while the worker's grant runs, because the grant's binding write reads the route again in its own transaction (`MemoryStore::bind_authority_route_unless_owned`): the worker leaves the root's authority with that identity, logs once per root `daemon: memory_reviewer leaves a switched root to the authority identity its route is bound to; its reviews start when that identity holds MODULE memories authority`, and reviews the root under that identity once it holds MODULE memories authority. The authority the worker takes covers memory reviews: the record's pass runs nothing for it and the History Summarizer hands it no fact set. The grant is stored and outlives the switch |
| Subjects | selection pages of the scheduler's slot, closed by `PRODUCTION_SELECTION_OPEN`, and fact sets; the record's pass runs every Ready job except a memory review | the worker selects each pass (`review_cycle::select_and_enqueue`): one job per decision over its `decision_summary` descriptor, for each memory that new evidence bears on, the memories eligible for a session's block first and the newest evidence first among them. The switched pass runs memory reviews alone |
| Claim descriptors | published by the search lifecycle owner | the worker runs the claim consumer itself on a host with no search lifecycle owner (`review_cycle::publish_claims`): at the start of a pass and, while a catch-up reaches the tip, again before each review, so the consumer then trails the Kernel's tip by one review at most (`Worker::catch_up_claims`; a catch-up runs at most 256 slices inside 30 s, and one that stops short is left to the next pass) |
| Question | the fact-set template `extracted_facts` | the memory template `memory_statement`, whose instructions list the four actions a memory admits (`revise`, `retain`, `retire`, `no_change`) and two read operations, a reference and related memories. A memory review opens no project inspection: a step that asks for a file of the working tree is refused as `unavailable` |
| Proposals | applied only by `review.accept` under the acceptance record | treated as `memory_reviewer.apply` says |

Selection under `memory_reviewer.review: memory`: review on evidence of change. A selection walks the store's live claim descriptors in object-id order, of every project and representation, examines at most 4,096 of them (`MAX_WALKED_DESCRIPTORS`), and keeps the project's `decision_summary` descriptors the configured model may read that name a stored memory: a decision of the `memory` domain other than a verifier's attestation (`review_cycle::names_stored_memory`). A decision of another domain and an attestation stay outside review. A store with more descriptors is covered over successive passes: the next selection continues where this one ended, and the worker logs once per project that it does (`daemon: memory_reviewer selection examines at most 4096 claim descriptors a pass, fewer where its statements share many terms, and the store holds more; each pass continues where the last one ended`). A walk ends before 4,096 descriptors where pairing its statements by subject terms would take more than 2^24 postings steps (`MAX_ASSOCIATION_STEPS`, the sum over terms of the squared count of the walk's statements that hold the term): the selection keeps the statements, in the walk's order, whose pairing fits, always at least one, and the next selection continues after them. A later memory reaches an earlier one when one walk examines both. A memory is enqueued when a later source that it does not cite may bear on it, and a memory has no such source at its creation. A source is later when it was written after the memory was stated (`review_cycle::written_later`). A message and a tool result are ordered by the time their descriptor carries (`review_cycle::source_time`: the harness's message timestamp, and for a tool result the end of its call): after the newest source the memory cites, or, for a memory none of whose cited sources the store still holds with a time of its own, after the time the Kernel recorded the commit that first stored it. A source stamped at that moment or before it is the memory's origin and brings it to no review, whenever its descriptor is published. This matters for a note the agent writes through the memory tool, which cites no source and is stored before source capture publishes the user's message and the tool results of that turn, and for a statement memory capture stored before its message's descriptor existed: the message the row restates is published after the row. The comparison with a commit's time reads two clocks, the harness's and the daemon's, which are one host clock in a deployment; a harness that stamps messages on another timeline, as a replay of old transcripts does, places every message before a note's commit, so a note is then reviewed on no message, and a harness clock ahead of the daemon's reviews a note on the message it was written from. A source is ordered by the stamp it carries: an OpenCode assistant block carries the completion of its message and a tool result the end of its call (a Pi row carries its message timestamp), so the text and the tool result of the very step that stored a note can be stamped after the note and then read as later. A repository document's revision counts observations, so it is ordered by commit: published after the commit that first recorded the memory. Later sources come from three places: the memory's contradiction-candidate rows (source text published after it that overlaps it; a row counts while the candidate reader serves it, written by this Kernel incarnation under the current matcher at or before the selection's tip), the source of a later memory that shares subject terms with it, and the source of the memory that contests it. A later memory of the same category reaches an earlier one on two shared subject terms, and one of another category on three, because capture can file one rule under different categories from one session to the next; each later memory names at most the four earlier ones that share most. A statement that a review marked contested (see "Apply modes") takes as evidence only sources published after the commit of that mark: every source that review was shown was published by then, and a source published by then that it was not shown is left out with them. A statement the user settled after a contest is the user's latest word, and takes as evidence only sources published after the settlement. Selection passes the records a recorder writes from a tool event and keeps current itself, by their decision kind (`TOOL_FAILURE`, `named_file_use`): they state nothing a later statement could replace. A subject term is an analyzed term of the statement outside a fixed list of words every statement uses, cut to its stem (without one of the endings `ing`, `ed`, `es`, `s`, and then without a final `e`). The writer decides whose evidence counts (`stage_one::takes_evidence`): a user's own statement and a fact the assistant reported take later sources the user wrote; a statement of work in progress, and a note that opens with no writer's label, take later sources from any writer. So a reported fact comes to review when a later user message overlaps it or a later user statement shares its subject. The reason is what a review can change and what it costs. The assistant restates and extends its own reports turn after turn, and its tool results repeat their words, so the assistant's later text would bring every earlier report back to review at each turn; a reported fact is served on explicit search alone, as a labeled row, before a dispute and after it, so those reviews would change nothing a session receives. The user's later word outranks a report and is the evidence a correction arrives as. Work in progress ends when anyone reports it done, and a note is the agent's own record, which its later messages and tool results may correct. A selection weighs 16 of a memory's candidate rows, in the candidate reader's order, highest overlap first (`review_cycle::weighed_rows`). When the store holds more than 16 rows for the memory, a served row that is not later evidence for the memory gives its place to the next row in that order. Such a row names a source the store no longer holds, a source the memory cites, a source from a writer the memory takes no evidence from, a source published by the mark or the settlement that set a statement's floor, or a source written at or before the time the memory was stated. The assistant's restatements of a report, which repeat most of its words, and the messages of a note's own turn, which capture publishes after the note, therefore leave a lower-ranked user message among the rows weighed. A row the candidate reader does not serve keeps its place. The selection reads the further rows in pages of 64 until 16 rows count or the memory's rows end; the store holds at most 4,096 candidate rows per project, which bounds those reads for all of a project's memories together. A selection enqueues at most eight jobs per pass: the memories eligible for a session's block first, then the rest, and within each group the newest evidence first. A memory is eligible for the block when it is of a positive category and the Kernel serves it on the automatic-injection surface (`review_cycle::automatically_delivered`, one read of the serving rows of the candidates in those categories); a memory of another category, such as `REJECTED_APPROACH`, is in the second group. Eligibility is a fact of the project. Which eligible memories one session's block holds depends on that session: its token budget, its `NAMED_FILES` lines, and its own captures, which its block leaves out. An eligible memory that a session's budget trims is therefore in the first group. When the pass limit, the hold bound, or the store's quota ends a selection, its room has gone to the memories a block can carry. The worker logs each job as `daemon: memory_reviewer enqueued job=<id> trigger=<contested|current_work|later_statement|later_message> later=<n> source=<n> delivery=<automatic|search>`; the last field names the job's group, `automatic` for the eligible group, and records no delivery to a session. A job's starting references are up to two message blocks the memory cites, first, and up to four later sources. A captured message is retained for 30 days, so each source's descriptor is read again when a job is enqueued: a job carries the sources the store retains at that moment, and a memory whose later sources are all retired is passed. The newest later source a job carries is its causal signal and names the job, so newer evidence reviews a memory again, and evidence that ages out of the store, as a candidate row does after 30 days, leaves the last review's name standing and starts none. A source's place in that order is the commit that published it, which stays the same whichever trigger brings the source up and whenever a later memory comes to cite it, so a statement memory capture stores for a message that was already reviewed starts no review. The store keeps no record of which sources each review was shown, and two cases depart from the rule. One more review on evidence already shown starts when the newest candidate row is removed out of age order (the store evicts the lowest score first at its bound of 4,096 rows per project, and a rescored source can lose its row) while an older source that never named a job remains. And a source that becomes evidence only after a review was shown a source published later starts no review; the next newer source brings both. Messages with equal text published in one commit share one evidence row and one place; a repeat published later is a source of its own at its own commit. A statement is ordered by the commit that first recorded it, which the rewrite of a contested statement's row leaves unchanged. A memory whose `retire` or `revise` proposal a reader has yet to settle waits for that proposal; the worker rebuilds the list of waiting memories from the project's active review holds once per process. A pass selects and runs at most as many reviews as the hold bounds leave: what is left of the project's 64 active review holds and of the host's 256 (section 6). With none left the worker selects and runs nothing for the project and logs the wait once (`daemon: memory_reviewer reviews of a project wait: ...`); reviews resume when a pending proposal is settled or its review window ends. A job that waits past its queue lifetime of 24 hours expires, and its evidence counts as reviewed. The store holds no record of a session's end and no link from a memory to the files it names, so a statement of work in progress is reviewed when later text bears on it, and a changed file brings no memory to review.

The run. For a memory under the memory template the host labels each linked reference with its writer (the source class the Kernel admitted the descriptor under) and its time (a message descriptor's revision), says whether the memory cites it, it was written after the memory's source (a reference with no message time, such as a tool result or a repository document, is one the selection linked as later evidence), or it is a message written with the source or before it, which the stage-1 state leaves out, and reads each once before the first request, so one request carries the statement, its source, and what was written later. A captured message is retained for 30 days and a memory outlives it; a run whose memory has no retained source says so in a host line, and its later references are labeled as written after the source. Related discovery for a memory delivers one stating form per decision, passes the subject's own decision and every rationale, and relates a candidate on three shared terms of the statement.

Stage 1, the decider. Every memory review is decided first by one short request (`Run::stage_one`, `crates/daemon/src/memory_reviewer/coordinator.rs`; the instructions and the flag rule are in `stage_one.rs`). A review whose state holds no later reference from a writer who may change the memory is a keep the host decides without a request. A proposal is the response of a completed attempt, and this review made none, so no proposal is staged: the receipt completes as the abstention `expectation_changed`, the memory stays as it is, and the job's name stands, so the same evidence starts no second review. The selection links a message only when it was written after the memory was stated, so this happens where the store changed between the selection and the run: the later sources a job was queued with were retired before it ran. A later reference of that kind that the run could not read ends the review by what its refusal means: a read the store failed ends the run unsettled for a later pass; a reference past what one run may read (the 128 KiB of model-visible bytes) ends it before any request as a `partial_disclosure` abstention, as a memory past that bound does; a reference the store has retired is evidence that is gone; and a reference the policy withholds from the model lets no keep be recorded. The review then ends on that refusal when no other such reference was read or when the decider keeps the memory, logged as `daemon: memory_reviewer review ended on a later reference the model was not shown: job=<id> refusal=<code>`, and goes on to the review model when the decider flags it. A keep the decider gave before that ending is logged on its own `stage 1` line with `decision=keep`, so a report pairs the two lines by job. Otherwise the decider is asked four questions about the review state: whether a later reference changes what later sessions should be told by the memory, how the strongest later reference relates to it, whether work in progress has ended, and which later reference is strongest. The state is JSON text in one fixed member order: the memory with who said it, its category, and whether it records work in progress; its source references; its later references with id, writer, time and text. The memory's text, category and work-in-progress flag are read from its decision row, and each reference's text is the buffer the opening read rendered for the configured-model destination. Every alias the state quotes, the memory's included, is revalidated, and the assembled request passes the render check as the JSON text and as the plain texts in order, so the `Secret` class, the secret scanner, and the render check hold at stage 1 as at stage 2. The request is an attempt of the job: it commits an attempt marker and records its terminal, and its state is charged against the run's 128 KiB of model-visible bytes like a resend. A state too large for one request, or for what is left of that bound, is flagged by the host without a request. A review the decider answers and does not flag settles at once as a keep: the host builds a `retain` proposal that cites the whole first source reference, or a `no_change` proposal with no citation when the store retains no source, and the review model is not asked. A flagged review goes on to the review model with the job's remaining attempts. The run logs each decision as `daemon: memory_reviewer stage 1 job=<id> decider=<chat_model|classifier> model=<provider/model> request=<digest> decision=<keep|flagged> changes=<answer> relation=<label> work_ended=<answer> strongest=<alias> later=<count>`, with no content (a decision the host made without a request reads `decider=none model=none request=none`), and each request that ended without an answer as `daemon: memory_reviewer stage 1 request ended without an answer: job=<id> decider=<kind> model=<provider/model> <refusal>`.

The default decider is a small chat model, reached through the host's model execution like the proposal request, so it runs on every harness and sends nothing to a provider the deployment does not already use (`disclosure::Disclosure::screen`). Its system text is fixed instructions that quote no review (`stage_one::system_text`, about 1,000 tokens), identical for every request so a provider can cache them, and the state is the one user message. It answers with one JSON object of four closed answers: `changes` and `work_ended` as `yes`, `no`, or `unsure`; `relation` as `replaces`, `adds`, `restates`, or `unrelated`; `strongest` as a reference id or `none`. A fenced object is read as the object, and a member beside the four is passed over. The flag rule (`stage_one::decide`): the review is flagged when a later reference from an eligible writer exists and `changes` is `yes` or `unsure`, or the memory is work in progress with a later reference and `work_ended` is `yes` or `unsure`. An answer outside the closed form, an answer cut at the output cap of 2,048 tokens, and a response the provider stopped all flag the review, so the review model decides it; the log line then reads `changes=malformed`. The model is `memory_reviewer.stage1_model`. Absent, `config::default_stage1_model` derives it from the review model's reference: a Claude reference carries its tier as the word after `claude-`, and the same reference with `haiku` there names the small model of the same provider, route, and version (`amazon-bedrock/global.anthropic.claude-opus-5-5` gives `amazon-bedrock/global.anthropic.claude-haiku-5-5`). Any other review model answers the stage-1 request itself; name a small model of that provider in `memory_reviewer.stage1_model`. A derived reference is a guess at the host's catalog. Until a request to it has answered, a request to it that fails for any reason moves the review's remaining stage-1 attempts to the review model, so that review is still decided; the worker then logs once that stage 1 uses the review model until the daemon restarts, and sends the project's next reviews there at once. The decider's answer is released only when the host reports it came from the stage-1 model, as at stage 2. An answer from another model than a named or proven stage-1 model ends the attempt with the `ModelMismatch` refusal and closes review for the rest of the process, as at stage 2.

A stage-1 request to a named or proven model that ends without an answer (a failed or timed-out host run; on the classifier route a failure code, answers outside the four typed answers, 20 seconds without an answer, or a full exchange of 64 parked requests) spends that attempt; the run pauses two seconds before its next attempt, and the project's other jobs stay queued for 60 seconds (`stage_one::FAILURE_COOLDOWN`), so an outage of the decider ends one job per minute as `budget_exhausted` and the rest are reviewed once it answers again. A failed host run that the host classes `auth_required` reports a credential the provider refused. On a stage-1 request to a named or proven model and on a proposal request it ends the attempt charged and closes review as `unavailable` for the rest of the process, as an answer from another model does, and the daemon log records it once as `daemon: memory_reviewer provider rejected an attempt (auth_required); the gate stays closed until the daemon restarts`. An unproven derived default that fails this way moves stage 1 to the review model, as any failure of it does.

Stage 1 by a typed classifier. Where the project names `memory_reviewer.classifier` and a harness of the project asked for classifier work within the last 120 seconds (`classifier::ClassifierExchange::present`), the classifier decides a stage-1 attempt in the small chat model's place (`disclosure::Disclosure::classify`); the run looks at that mark before each attempt. A harness asks every two seconds and submits within about twelve seconds of its pull, so the daemon takes a request that waits ten seconds or more and receives no submission as the harness having left (a harness still running restores the mark with its next call): that attempt is spent, the mark ends, and the small chat model decides the run's next attempt and the reviews that follow. A harness that closes during a classifier call submits `cancelled`, which ends the mark the same way. The Pi harness also submits `cancelled`, and stops asking, when it pulls work once the classifier's credential is gone, and a Pi session that leaves the project stops asking for it at its next lifecycle event. A classifier named while a session is open is answered by sessions that bind after the change, because a route answers classifier work by the configuration it loaded at its bind; the Pi plugin reads its configuration when Pi starts, so Pi answers for a newly named classifier after it restarts. Its request is the same state and the same four questions as typed questions, sent as JSON text in a fixed member order because a classifier's answers move with that order. The attempt marker names the provider `harness-classifier`, the classifier reference as the model, and the credential `harness-registry`, and the run waits at most 20 seconds for the harness's answers (`docs/host-wire-protocol.md` Section 7.11). The classifier answers with probabilities, and the review is flagged when a later reference from an eligible writer exists and the probability of a change is at least 0.5, or the memory is work in progress with a later reference and the probability that its work ended is at least 0.5 (`classifier::decide`). The harness calls the classifier under its own registry and credential, so with this key set the memory and the messages under review go to the classifier's provider; `Secret`-class text is excluded as on every route. A project that names no classifier, or whose harness makes no classifier call (a Pi whose model registry lacks the classifier surface or a configured credential for the classifier, OpenCode), is decided by the small chat model. The classifier surface was checked against Pi 1.6.0. `@eidnara/pi` declares the peer range Pi `^0.80.2` and CI tests Pi 0.80.2, whose model registry has no classifier surface (`packages/pi-plugin/src/memory-review-classifier.test.ts` holds that registry to it), so on the declared range the small chat model decides. A Pi that has the surface is newer than the declared range; the plugin answers classifier work on it, and the tests of that path run against hand-built registries.

Stage 2, the review model. The memory template tells the model that `retire` needs a later reference about the same subject and the same slot (which kind of name, which position, which tool, which setting), that a later rule for another kind of name, position, tool, decorator, import or scope adds to the memory, that a statement of the user changes only on a later message the user wrote while an "Assistant reported" memory may also change on a later assistant message or tool result, and that `low` uncertainty is for a later reference that names the same subject and slot in its own words. The system text opens with a host directive that asks the harness for the text as written, so a Pi child adds no date or working-directory line to it (`host_runtime::model_execution::backend::PLAIN_SYSTEM_DIRECTIVE`). An answer wrapped in one Markdown code fence is read as the step it wraps. A response the provider stopped itself, as a content filter does, settles the review on that request as `model_declined`. A memory review that reaches its inspection ceiling keeps the proposal the model gave on the references it read, with a limitation that says so; at the proposal's bounds of 16 limitations and 32 KiB of text the model's last limitations give way to it.

Change detection at a session's end. `memory_reviewer.review` says what the switch reviews. Under `session`, the default once the switch is set, a pass reads a session that ended beside the statements the project delivers (`memory_reviewer::change_detection`), and stored memories are not reviewed one by one; under `memory` the worker selects and reviews each stored memory on later evidence, as the paragraphs above and below describe, and reads no session. `apply: propose` writes nothing a reader has not accepted, so under it the switch keeps the per-memory review whatever `review` says; `contest` and `apply` write the session review's changes as the table below says.

When a session is read. A session is one harness's session: the pass groups message descriptors by the harness that published them and their session id. A pass considers the project's four most recent sessions by their newest message (`change_detection::MAX_SESSIONS_CONSIDERED`) and reads the oldest of them whose newest user block, by publication, no pass covered, one session a pass. On the worker's own loop, which runs every 30 seconds, a session waits until its newest message is ten minutes old (`change_detection::QUIET`) or a session that started after that message has begun, so the session before a newer one is read at once and two sessions running side by side wait for their own quiet. A caller that drains the worker, as the fixture host does after each session of a scripted run, marks a session's end, and every candidate is then read at once; the shipped daemon has no other signal of a session's end, so in a live deployment a session is read ten minutes after its last message or once a newer one starts. A message's age compares the harness's stamp with the daemon's clock, one host clock in a deployment; a harness stamp ahead of the daemon's, which source capture bounds to one hour, delays the read by as much. A project with more than 32,768 message descriptors is not read until its tip moves, and the worker logs once per project that its scan stopped at that bound. A pass waits while capture's queue for the project holds a pending or prepared job, so the statements capture takes from the session's messages are read beside them; after 30 minutes of one unsettled stretch (`change_detection::CAPTURE_WAIT`) it reads the session beside the statements capture has written so far, until the queue settles. The wait and its end are logged once each per stretch. The queue counts jobs capture enqueued; a capture checkpoint admitted and not yet enqueued does not hold the pass.

What a request carries. The statements are the rows a new session of the project receives in its block now under the user tier's `memory_budget_tokens`, the newest session's own rows among them (`canonical_memory::delivered_rows`); work in progress is listed with `"work": true`, and a statement taken from a message of the session read names it under `"from"`. Capture rows record the session and native message id of their message and no harness, so a statement's source is matched by those two. The session's user messages are read from their descriptors' exact evidence: the messages no earlier pass covered first, newest first, then covered messages as context, newest first, while their encoded request entries fit 24 KiB and at most 512 messages, each text cut at 6 KiB; a message's blocks are read only when it is picked, and the request lists the picked messages oldest first. Once a picked message does not fit, it and every message after it are counted as `left_out` and not read. A message is withheld when a block of it is `Secret` or refused by the Kernel's egress verdict for the configured model (`ArtifactDestination::ConfiguredModel`, the verdict the per-memory broker reads), has a block index or span that does not read, is not UTF-8, or fails the windowed render check over its whole joined text, the part past the 6 KiB cut included; a statement that fails the render check is left out too. A message whose verdict or read failed is `unjudged`, and a pass with one is tried again (below). One request to the review model (`memory_reviewer.model`) carries the statements and the messages as JSON, after fixed instructions that quote no project (`change_detection::SYSTEM_TEXT`); statements past 24 KiB split by section into at most four requests; before each request the Kernel judges every message block again at its own revision and the delivered block is read again, and a request whose message or statement line, a contest's excerpt included, changed or was refused since the read is not sent and leaves the pass to try again. Statements past the requests, or larger than one request, are not read by the pass, which counts them as `omitted` in its log line. A request the render check refuses is not sent and is counted as `render_refused`. The model names each statement a message changes, with the effect (`replaced`, `narrowed`, `moot`, or, for work in progress, `ended`), the message, the message's words, whose words they are, and its confidence; an answer with more than 64 changes is read as cut short. The pass writes only after every request answered, from the whole set of answers, and an answer that names one statement more than once is applied from its latest message.

What the daemon writes. A change is written only when the statement and the message are ones the request listed, the words stand in that message exactly, no earlier pass covered the message, the message is not the one the statement was taken from, the message is later than the statement, and `ended` names work in progress. A message is later when it was written after the message the statement was taken from, when the pass's scan holds that message, and otherwise when it was published after the statement was first recorded. Each change is one Kernel commit keyed by the statement's lineage (the commit that first recorded it and its text, which a contest keeps) and the message as the pass read it (its blocks, each by descriptor and bytes), with the effect, the action and the words in its request digest, so a replayed pass writes nothing twice and a retry that reads the same message another way is refused. The commit first checks that every block of the message is still live, holds the bytes the pass read, and is served below `Secret` and not hidden on explicit search, and that the statement is still the row the pass read and one capture wrote; a session deleted or reclassified while the request waited, or a statement another writer changed, writes nothing. A finding that writes nothing rolls back and holds no key. A row for the user's words is recorded only while capture's consent holds for the root (`memory_enabled` and `auto_promote` in the user tier and in the root's own load, and the user tier's `memory_auto_capture`); without it a finding is written only when the block delivers a capture row of the same session and message whose quotation holds the words, and that row is named. A row is named, and a row the review recorded for the same words before is used again, only while the Kernel serves it as the action needs at the commit (delivered for a replacement, on explicit search at normal sensitivity otherwise); otherwise the finding writes nothing. What a pass writes keeps the change undoable and visible on explicit search:

| Effect, high confidence | Write |
| --- | --- |
| `replaced`, the words are the user's own whole sentences of the message | the words are recorded as the user's statement of that message (`memory_capture::record_reviewed_sentence`) and approved for delivery, or capture's delivered row of them is named; the old statement is superseded by a labeled row of the same text whose rationale records `changed_by` (the effect, the new row, the session and the message), which explicit search renders as `Changed (replaced) by <id>` (`docs/host-wire-protocol.md`, 7.9) |
| `replaced`, words the user passes on, part of a sentence, or words that end where the message was cut at 6 KiB | the old statement stays delivered and its line is marked contested by a labeled row of the words |
| `narrowed` | the statement stays delivered and its line is marked contested by the words, with both dates |
| `moot`, the user's own whole sentences | the statement is superseded by a labeled row whose `changed_by` names the effect and the row of the words |
| `ended`, the user's own whole sentences | the work leaves the work section and stays on explicit search as ended (`ended_by`); a `replaced` or `moot` finding on work in progress ends it the same way |

An answer the model gives with low confidence, a finding on words the model did not read as the user's own, and a `moot` or `ended` finding on words that are not whole sentences of the message or that end where the message was cut, mark the statement contested at most. A finding reads as the user's only when every finding of the pass whose words overlap it in the same message does too. A recorded row of the words carries the speaker the pass settled (`user` or `other`), or none when the model named none or the readings disagreed. Each pass records a receipt for the newest user block of the session it covered, so a session is read again only when it holds a newer user message: the messages an earlier pass covered are then sent again as context and ground no change. A request that fails, an answer cut short, an answer outside the closed form, an unjudged message, and a change that fails to commit for a reason other than a conflict leave the session uncovered and write no change; it is asked again after one minute from the failure, the wait doubling at each failure. After the third failed attempt that reached the model, or that an unjudged message held back, at the same newest message the session is recorded covered with no answer, and the receipt's payload says the attempts were spent (`change_detection::MAX_ATTEMPTS`, `RETRY_AFTER`); a request that never left the daemon waits without counting. A pass that settled everything but its receipt writes only the receipt on its next try, after the wait. The count is held by the running daemon for at most 4,096 frontiers, keeping those whose counted attempts still gate a request, so a restarted daemon counts afresh. A provider's refusal settles its request with no change. An answer from a model other than the configured one, with or without a usable body, and a refused credential close review for the rest of the process, as on the per-memory route (section 6). Session requests go through the host's model execution with the per-memory route's request bounds; they are not recorded in the attempt ledger and spend no review hold, and the attempt bound above is what bounds them. A root whose path names another project than the one its route bound is left unread and logged. The worker logs each pass as `daemon: memory_reviewer change detection session=<16 hex> messages=<n> withheld=<n> unjudged=<n> left_out=<n> statements=<n> omitted=<n> requests=<n> render_refused=<n> findings=<n> ungrounded=<n> replaced=<n> contested=<n> retired=<n> ended=<n> refused=<n> covered=<true|false>`, with ` after its last attempt` when the bound recorded the session, and with no content.

Apply modes and the action rule. After a run publishes a proposal, the worker treats it as the mode says (`review_cycle::apply_proposal`). A `retain` or `no_change` proposal asks for no write, so every mode accepts it at once: the acceptance leaves the memory as it is and the worker ends the proposal's review hold (`settlement::release_settled_review_hold`). The project's hold allowance (section 6) is then spent only on proposals that wait on a decision. A `retire` or `revise` is acted on only inside the action rule (`review_cycle::actionable`): stage 1 flagged the review; the model stated `low` uncertainty; and a contradiction cites one of the review's later references from a writer whose word counts for the memory (the user for a statement and for a reported fact). The memory's own source, a related memory, and any other alias the run was given are no such reference. The stage-1 decision and those references are held in memory from the run to the proposal's treatment in the same pass; a proposal adopted after a restart has neither, so its change is dropped. A daemon that stops after a run's receipt completed and before the worker treated its proposal treats that proposal in no later pass: a completed job is not run again. The proposal then waits under its review hold as one `propose` leaves for a reader, a `retain` or `no_change` included, until `review.accept` or the end of its review window.

A `revise` of the user's own statement inside the rule is treated alike in `contest` and `apply`. The model proposes `revise` when a later statement replaces part of what a statement says, as when one sentence gives two rules and the user later changes one of them. The reviewer writes no successor text for a user statement, and removing the statement would take the part that still stands out of delivery. So the statement stays delivered and is marked contested by the memory capture stored for the later message the proposal cites (`review_cycle::contest_with_later_statement`, `memory_capture::contest_reviewed_statement`): its block line reads `<statement> (stated <date>; contested <date> by <memory id>: "<the later statement>")`, the presentation capture's own contests use, and the later statement is delivered on its own line. When capture stored no memory for the cited message, or the statement is one a contest cannot rewrite, the statement stays as it is. The lookup of that memory (`review_cycle::later_memory_citing`) reads the store's claim descriptors to their end at one tip, 4,096 a walk, and keeps the best match and the cursor between walks. Each Kernel read of a walk starts only inside one 30-second budget and finishes the walk it started. A store the budget cannot cover ends the lookup as a refused write: the proposal stays unapplied under its review hold, the statement stays as it is, and the worker logs `left a published proposal unapplied`. Otherwise the worker logs `contested` or `standing`.

In `contest` a `revise` inside the action rule of a memory the assistant reported writes nothing: the proposal says part of the memory still holds (a line number moved, one of two values changed), `contest` writes no successor text, and a dispute would take the whole row. The memory stays as it is, its review hold ends, and the worker logs `standing`. This is the rule a user statement follows, without the contested mark, which only an approved statement's row can carry. A `revise` of a note, which carries no writer's label, is disputed like a `retire`.

For every other `retire` or `revise`:

| `memory_reviewer.apply` | Effect |
| --- | --- |
| `propose` | nothing; the proposal waits for `review.accept` under its review hold, and the memory waits for the proposal. `review.accept` needs the owner's acceptance record; without one the proposal waits until its review window ends, at most 7 days |
| `contest` | the default. Inside the action rule a `retire`, or a `revise` of a note, records `mark_disputed` on its target, citing the first contradiction that cites one of the review's later references; the statement leaves automatic delivery and stays on explicit search as a labeled row, and the proposal waits for `review.accept` under its review hold, as in `propose`. Outside the rule the proposal is dropped: its review hold ends and the memory stays as it is |
| `apply` | inside the action rule the worker accepts a `retire` through `accept_selected_proposal`, the Kernel acceptance `review.accept` runs, which removes the statement from delivery and search. A `revise` of a memory that is not the user's own statement is accepted the same way: it supersedes the statement with a model-inference successor that explicit search serves as a labeled row. A `revise` is accepted when its new text opens with the memory's own attribution and holds no other writer's label anywhere, whatever the case; any other `revise` (`User stated` on a fact the assistant reported, also mid-sentence) is dropped. Outside the rule the proposal is dropped as in `contest` |

Review holds. A published proposal keeps a review hold until it is settled or its review window ends, and section 6 bounds the active holds of a project (64) and of a host (`MAX_ACTIVE_MEMORY_REVIEWER_HOLDS_PER_HOST`, 256). Under the switch the worker ends a proposal's hold when it settles the proposal: every `retain` and `no_change` at once, every change proposal outside the action rule, every proposal `apply` accepts, every `revise` of a user statement, and in `contest` every `revise` of a memory the assistant reported. A proposal that `propose` leaves for a reader, and one whose target `contest` has disputed, keeps its hold until `review.accept` settles it (`wire::handle_review_accept` ends the hold after a new and after a replayed settlement) or its review window ends, so the allowance bounds those: at most 64 per project at one time, each for at most 7 days. With no hold left under the project's bound or the host's, the worker selects and runs nothing for the project until a hold ends.

Read freshness. A gated `kernel.read`, which explicit search's snapshot scan asks for, and the Kernel health block measure the lag of the consumers a search serves from (`kernel_routes::serving::unserved_consumers`, `KernelStore::outbox_lag_excluding`). The claim consumer is one of them on a host whose search lifecycle owner runs it, because its descriptors reach the search projection there. On a host where the review worker runs it, its descriptors serve review selection alone, so its lag is left out: a review that runs past the 60-second age threshold (`serving::LAG_AGE_THRESHOLD_MS`; one run may take 120 s) leaves a gated read, `required_consumer_count`, `lag_threshold_tripped` and the daemon's health status as they are with the switch off. Where a consumer a search does serve from lags, the snapshot scan still answers: it ranks the canonical rows of the tip, which each commit writes itself, repeats the read ungated, and adds the note `Memory: a search consumer is behind recent changes. These results are read from the canonical tip and include them.` to the result. The block a session receives is composed from canonical rows in every case. A status surface reads as explicit search does (`readSearchMemorySnapshot`): where the gated read answers `stale` or `no_required_consumer`, the OpenCode sidebar and the Pi status dialog count the rows of the same read repeated ungated and show that state beside the count. The claim consumer's checkpoint still bounds what the Kernel keeps for replay, as every registered consumer's does (`KernelStore::prune_outbox`, and the descriptor evidence `cas/gc.rs` withholds as `UnacknowledgedReplay`). A claim consumer that stops advancing while the worker runs it is reported by the worker's `claim catch-up is blocked` or `claim catch-up failed` log line, once per pass. The health block does not report it: `retained_outbox_rows` counts every outbox row, whichever consumers have read it. With the switch turned off the worker runs no catch-up and logs nothing, and the consumer stays registered at its last checkpoint. A host in that state keeps no more for replay than a host with no registered consumer, which has no replay horizon and keeps all of it.

Trigger. The worker's loop runs a pass every 30 s while idle and at once after a pass that settled a run. `Worker::drain` runs passes until one settles nothing, which is also what a pass does while a project's reviews wait (the 60 seconds after a failed stage-1 request, or no review hold left); the fixture host exposes it as the `review-drain` control, which a replay harness calls after each session.

under the same owner-only rules as the runtime identity record. ### Bedrock: schema 2

A deployment whose model credential is the `amazon-bedrock` row activates the reviewer with a schema 2 record. The sender then calls `InvokeModel` on `bedrock-runtime.<region>.amazonaws.com` with the Anthropic Messages body (`"anthropic_version": "bedrock-2023-05-31"`, no `model` and no `stream`) and signs each request with SigV4 (service `bedrock`) after the connection is open and before its attempt marker commits; nothing on this path reads `ANTHROPIC_API_KEY`. The record carries every schema 1 field with these values:

| Field | Meaning |
| --- | --- |
| `schema` | `2`. |
| `model_id` | The Bedrock model id or cross-region inference profile id the request path invokes, such as `us.anthropic.claude-sonnet-4-5-20250929-v1:0`. Only a schema 2 record has it. One validated region feeds the host, the TLS server name, the signing scope, and the fingerprint. A rotated secret under the same key id keeps the same identity within a start; a new key id closes the gate as `identity_mismatch` until the record names it. AWS credentials never enter the harness selection's identities, so rotating them never refuses a restart.

### A rejected attempt closes the gate until restart

A 401 or a 403 from the provider, or a response reporting another model than the record's `model`, ends that attempt charged with no text released and closes the gate as `unavailable` for the rest of the process. The status alone decides: a 401 or a 403 whose body is compressed, past the job's remaining allowance, or stalled past the frame idle limit latches the same way, and its body is charged as any refused body is. The worker checks this before it reads the record, and every later pass reports `unavailable` again, claims nothing, and sends nothing, so a refused credential or a wrong model spends one attempt rather than one per job. The daemon log records the rejection once: `daemon: memory_reviewer provider rejected an attempt (status 401); the gate stays closed until the daemon restarts`, or, for a model, `(reported model "<id>" for "<model>")`, with the reported id cut to 128 characters and escaped; no response content is logged. The owner corrects the credential or the record's `model` and restarts the daemon, which clears the latch; every start already needs a refreshed record. A 429 or a 5xx spends the attempt as before, and the job's remaining budget decides whether another is made.

### Response budgets are the job's

A job may consume at most 1 MiB of raw provider response bytes and 64 KiB of decoded assistant text across every round, physical attempt, recovery, and generation; the per-response constants in the sender and decoder are the same numbers, so no single response can spend more than the job has left. Every attempt row records what its response consumed, written in the same statement as its terminal: the raw body the transport delivered and the text the decoder measured, on a completed response, a provider error body, a malformed body, and a cancelled or timed-out read alike. A `not_dispatched` attempt records zero. An attempt that is unterminated, `unknown`, or terminal without recorded bytes counts as the whole ceiling, because nothing durable says it consumed less; a failed terminal write therefore spends the job's remainder rather than granting fresh headroom.

The remaining allowance is computed inside the marker transaction, before the marker is inserted, over every generation of the job. A job with nothing left in either ceiling is refused there as attempt exhaustion, so no marker is charged and no request byte is sent; the run settles `budget_exhausted`. The two remaining values travel with the handed dispatch: the collector charges each chunk against the raw remainder before appending it and refuses the response where a chunk crosses it, recording the whole remainder as consumed; a declared content length past the remainder refuses before the body is read; the decoder charges each decoded text length against the text remainder before allocating it and refuses the same way. A compressed body is still refused before decompression, and nothing reads extra bytes to measure them. No store owner is held across a network await, and no durable write happens per chunk.

Adding the two usage columns changed the Memory Store baseline digest. A database created under the previous baseline refuses to open under this binary, and the previous activation record fails closed on `memstore_baseline_digest` until the deployment owner writes a renewed record; there is no migration, silent reset, or change to the Kernel baseline.

The store maintenance release changed the Memory Store baseline digest again. The baseline drops the `tag_cache_generations` table and its three `tags` triggers, so deleting a session's tags costs work linear in its tag count. It adds `chunk_transcript_totals`, a per-session compressed byte total that three `chunk_transcripts` triggers maintain, and the `idx_chunk_transcripts_session_age` index, so transcript eviction reads one total row and seeks its oldest victim instead of summing every row. `chunk_transcripts` stores `created_at_ms` and a generated `transcript_bytes` count ahead of `transcript_deflate`, so the triggers and the index read a deleted row's size and age without reading its transcript. A database created under the previous baseline refuses to open under this binary and is left untouched; recreate it with the Memory Store reset in section 5. The previous activation record closes the gate as `identity_mismatch`, and the daemon log names the term with its live value: `activation record names another memory store baseline; the live value is <digest>`. The deployment owner writes a renewed record naming the new `memstore_baseline_digest` and the new store's `memstore_incarnation`. There is no migration, silent reset, or change to the Kernel baseline.

While the gate reads anything other than `open`, including before the worker's first evaluation and after an evaluation goes stale, the History Summarizer reserves no MemoryReviewer job for an accepted fact set. The publication records the nonadmission `memory_reviewer_unavailable` instead, so a closed gate holds no review capacity. A firing that already holds a reservation republishes or settles it through its existing path whatever the gate reads.

## 3. Status

`host.status` carries `metrics.memory_reviewer` (wire document 7.6). Its `memory_reviewer_state` and counters are the sampler's; its `activation_state` is the worker's: `open`; `unknown` before the first pass; `stale` once the last evaluation is older than 300 s, which means the worker stopped evaluating and nothing vouches for `open`; or the closed reason's kind (`missing`, `refused`, `unreadable`, `malformed`, `identity_mismatch`, `unacknowledged`, `unknown_credential`, `unavailable`, `store`). Every counter is a count or a byte total; nothing on this surface names a project, a payload, or a person.

The scheduler enqueues Memory Classifier review selections only while the gate is `open`, so a closed gate does not fill the queue with jobs nothing may run. Jobs already queued expire at their queue deadline and the sweep records them as expired; they are never silently dropped.

### Production selection gate

Selection by the Memory Classifier's scheduled slot over the production classes, `canonical_claims` and `promoted_memory`, is closed by the constant `PRODUCTION_SELECTION_OPEN` in `crates/daemon/src/memory_reviewer/selection.rs`. The gate is separate from activation: an open activation gate schedules no production selection while this constant is `false`. A project under the review switch is selected by the worker's own pass for the configured-model destination (section 2, "The review switch"), and this gate leaves that selection as it is.

The coordinator does resolve both classes. A canonical or promoted descriptor names its originating decision in its leading identity field (`object_id` or `decision_object_id`), and the coordinator reads it through `ReferenceExpectation::CanonicalSource`, binding the descriptor's revision together with the decision's live revision. The broker judges both on every read, so a retracted, superseded, hidden, or re-revised decision revokes every form derived from it. Multiple descriptors of one decision share that decision as their owner and do not count as independent corroboration.

A proposal over such a descriptor targets the originating decision, not the descriptor: `ProposalTarget::Memory` carries the decision's object id, source revision, the snapshot read, and the decision's last change as `commit_token`. The descriptor stays a causal input under `ReviewTarget::Memory`, so the job's causal identity is unchanged. A decision whose revision moved after the run bound it refuses the proposal instead of retargeting.

The gate stays closed because no production representation of a decision is eligible for the Remote destination. Kernel ingest stores any artifact without affirmative repository provenance as `Sensitive`, only Git commit publication issues that provenance, and Remote egress refuses `Sensitive`. The production selector therefore admits none of them: its Remote fold denies every descriptor the production claim materializer publishes, whose artifact is `SensitiveRemote` for that destination, while the descriptor stays live and permitted to a local reader. A production-class job that ran anyway would resolve through its decision and abstain `owner_sensitive` before any request, with no attempt row, no connection, a `not_selected` read, and no Kernel commit. `memory_reviewer_worker::production_classes_are_refused_the_remote_model_at_selection_and_in_the_coordinator` witnesses both halves over both classes with no class override, and the broker's Remote refusal test shows zero disclosed bytes. `memory_reviewer_worker::fixture_canonical_and_promoted_forms_reach_readable_proposals_targeting_their_decision` drives a canonical and a promoted descriptor of one decision through the same selector, slot enqueue, and worker to selected, readable proposals whose target is the originating decision at its exact tokens; their evidence carries repository provenance the test supplies, so it is a fixture witness of the path and not production eligibility. The owner's decision-egress choice (#709) is that no decision bytes go to the Remote reviewer, so the gate stays closed and the production positive witness stays open. Opening it would require two things that choice withholds: an approved decision representation that is Remote-eligible under existing policy without caller-supplied provenance, and a positive production-class witness that reaches a selected, readable proposal through the real selector, coordinator, and stores. Resolver wiring alone is not eligibility, and neither the test-only Git commit class nor the fixture provenance is a substitute.

### Selection service

A Memory Classifier selection slot resumes its project's frozen page before it selects anything new, so targets that arrive while a page waits never pass it: full pending capacity defers the page with its due slot claimed and its cursor unchanged, every retry, across later cron instants, is that slot offering the same page, and once capacity returns that page is enqueued first and the next slot selects the arrivals from its cursor. The metadata quota clears only as jobs and pages retire (section 6): a page it refuses completes its slot as `memory_reviewer_selection_refused` naming the quota, stays frozen, admits nothing, and leaves the cursor and every recorded outcome as they were, and the next cron slot re-offers that page instead of selecting past it. A page that outlives its 24-hour selection deadline is expired by the sweep and its slot ends expired on the ledger under that slot's own command id; the next slot is a new selection under a new attempt identity from the recorded cursor. When such a renewed page enqueues, a target already admitted replays its recorded row, whose queue deadline, attempts, and outcome never reset, and only targets no page admitted become jobs. Expiry is not service: it records that the page was never enqueued. An enqueue whose bookkeeping cannot commit, at any reference's job row, the page transition, or the continuation, rolls back whole: the page stays frozen as it was, no reference becomes a job, the cursor stays, and earlier outcomes stand.

A slot's walk reads live descriptors in batches whose first holds the page's room (eight rows) and which double to 64, so a page that fills from its first rows reads and judges eight. A selected target needs a permitting Remote verdict and no job at its causal inputs; either check may run first, and after a batch in which most rows the ledger checked already had a job, the next batch fingerprints and deduplicates its rows before it judges eligibility, and judges only the rows without a job. A fully reviewed inventory therefore costs a ledger read per row, a remotely denied one an eligibility judgment per row, and both select the same rows in the same order. Each batch's linked evidence is one Kernel read and its dedup one ledger read. Quota checks read `memory_reviewer_metadata_totals`, which the baseline's insert, update, and delete triggers keep equal to the receipt charges plus allowances over each project's jobs and frozen pages, so admission reads one row per project however many receipts the store incarnation keeps. Lease acquisition collects expired claims through indexes on their terminal age, so its work follows the claims it redacts and deletes.

The eligibility half of the production path is witnessed with a repository-backed commit: the Git publisher issues its provenance, the production selector function picks it under production policy versions when given the test-only `git_commits` class, the store primitives the selection slot composes admit it under the slot's own identities, and the production worker runs it to a readable, non-abstaining proposal. The decision-derived classes take the same path in the fixture witness named under the production selection gate above; the production-class positive witness stays behind that gate.

### Causal reconsideration

A selected target's causal inputs are the memory at its live revision, the fixed question, the caller's policy versions, and its required evidence with availability. The required evidence is the descriptor's own evidence row and, for a decision-derived descriptor, the evidence its originating decision cites, itself or through its events: at most `MAX_LINKED_EVIDENCE` (8) rows, most recently cited first, read at the selection's tip through `KernelStore::linked_decisions_evidence_within_budget`, the batch form of `linked_decision_evidence_within_budget`, each with whether it is live. That read walks the decision's events newest first, stops once the eight newest citations are settled, and never reads past its newest `LINKED_EVENT_WINDOW` × 8 events, so one target's enumeration is bounded whatever the decision's history. Each batch of examined descriptors costs one Kernel read for the linked evidence of its rows still in question and one Memory Store read for their job lookups. A new citation by the originating decision changes the causal identity at an unchanged target revision, so the next selection reconsiders the target once under a new job; so does a cited row among the eight that stops being live, which a citation's own liveness rule leaves to a later invalidation such as an operator's artifact deletion. Repeated selections at unchanged inputs pass the target while its job row stands (section 6 retires a settled job after ninety days); re-citing a row already among the eight moves it to the front and leaves the set unchanged while the eight still fall within the newest `LINKED_EVENT_WINDOW` × 8 events, and a citation that window edge passes leaves the set, which reconsiders the target once more; a prior outcome stays recorded under its own identity. Writes to other objects, clocks, and selection-attempt identities never enter the inputs. Citations older than the eight newest, and their liveness, are not part of the fingerprint; a linked evidence id longer than the ledger's 256-byte identity bound is left out rather than hiding the target; evidence not linked to the originating decision does not retrigger a target.

The mechanism is proved through the real Kernel, selector, and ledger with a decision-derived descriptor the fixture makes Remote-eligible by repository provenance on its evidence and an admission on the descriptor. Production reach stays behind the production selection gate above until a decision representation is Remote-eligible under existing policy.

## 4. Review reads

`review.list` and `review.read` (wire document 7.8, protocol 3) are the only ways to see what the MemoryReviewer concluded. Both are local reads of the bound project's completed outcomes and the proposals their receipts select. A proposal is readable only while its receipt is complete, its selection matches, and its review hold is live; the review hold's expiry is the only review deadline, and selection never refreshes it. An abstention lists with its reason and has nothing to read. Neither operation depends on the activation gate: an outcome already recorded stays readable while new disclosure is closed.

### Private results and the queue deadline

A run's Kernel result and its execution-to-review hold transfer commit before the Memory Store completes the receipt, and only the completed receipt selects the result for publication. Staging, sealing, and the transfer share one Kernel envelope; the transfer runs under a savepoint, so a refused transfer still commits the sealed row, which a later settlement or adoption of that generation transfers on its own. The staged proposal row keeps the job's 24-hour queue deadline through the transfer; the transfer proves retention, not selection, and never moves a deadline. Until a receipt selects it, the row is private: `review.read` answers `not_selected`, and a Kernel read of the row by identity expires at the queue deadline even though its review hold runs for up to seven days.

A result the Memory Store selects before the queue deadline is read against its selection time, which completion fences against that same deadline. Such a result stays readable after the queue deadline exactly as long as its review hold is live and every disclosed input still passes local policy; the hold's expiry is what ends it. A receipt the sweep closed as `expired`, `unknown`, or `cancelled`, a rejected or losing generation, or a late completion fenced by a terminal cannot publish the row or refresh either deadline.

### Recovery without the run

A run's broker, alias table, and transcript live in the worker process. A worker that resumes a claim after a restart, or a successor that takes a receipt over, has none of them. Every proposal row therefore carries a dependency record beside its payload: the complete policy union the run disclosed, with each member's kind, id, revision, owner, and owner revision, and the attempt marker whose response the proposal is. The record lives in the row's witness, not in the payload, so the payload bytes, their digest, and the `review.read` wire shape are unchanged.

Before a resumed run resolves its subject or takes any evidence work, it reads the job's attempt markers. A generation with no marker, or with only `not_dispatched` markers, proceeds as a fresh run under the original identity, deadlines, and remaining attempts, unless an earlier generation left an unterminated or `unknown` marker: that marker already makes the job's outcome unknown, so a successor that took the receipt over sends nothing and completes it `unknown` rather than paying for an answer its settlement would discard. Any other marker at the run's own generation means a request was dispatched whose answer this process never saw, and the run sends nothing:

- A sealed proposal row at the generation's provisional identity is revalidated from its record: the union bytes must re-encode to their digest; the marker must be a completed attempt at that generation with the recorded body and union digests; every member is rebuilt from the live store and judged as a live run would judge it, including uncited members and each canonical member's originating decision and its revision; the members must produce exactly the payload's disclosed inputs and ancestry. A row that passes is published exactly as a live settlement would, under the review hold the lost run transferred or, when it had not, under this run's execution hold, extended over the record's inputs first because a hold recovered or replaced after an unsettled exit may cover nothing. Zero model requests.
- A row that fails revalidation, or a row staged without a record, ends the receipt `abstained` with the reason revalidation names. Nothing infers lineage from the payload, and no migration rewrites old rows.
- When no sealed row exists, the receipt completes `unknown`. A committed marker with an unknown outcome is not authority to send again.

A takeover advances the generation, so a successor adopts only a result of its own generation; the losing generation's row stays sealed and private. The selected read runs the same revalidation for a local reader on every `review.read`, so a proposal whose cited or uncited lineage moved after selection answers `dependency_refused` while the receipt still selects it.

The record widens the witness a proposal row is stored under. A binary from before this release decodes a witness only in its own shape, so it refuses every proposal row this release stages (`scope_mismatch` on read, and a settlement retry on that binary cannot recover its own sealed row). No schema baseline changes, so the store opens, but the rollback rule in section 5 still applies: an earlier binary runs only against the backup pair it wrote, never against a live family this release has staged into.

The sweep closes an in-progress receipt at the earlier of its run deadline and its job's queue deadline. Each lifecycle pass then reconciles the review holds of the live Memory Store incarnation: a hold whose result no completed receipt selects and no in-progress receipt can still select is released, so the hold and its quota charge end at the next pass rather than at the review expiry. The transfer had already moved each MemoryReviewer capture's `retain_until` to that expiry, and the release does not move it back: the capture's evidence and artifact bytes stay until the capture sweep retires them after `retain_until`, whether or not a hold still pins them. Selected results keep their holds; holds of another store incarnation, such as a restored Kernel's beside a replaced store, are left alone; nothing is rescued, refreshed, or accepted by this pass.

### Kernel acceptance

`KernelStore::accept_review_proposal` applies the proposal a completed receipt selects. The caller passes what it copied from the trusted receipt (the run binding with project digest, both incarnations, the job's causal identity, and the generation; the selected row's id, Kernel incarnation, and payload digest; the completion time), the target it read, the revision of the question template it runs, and its own idempotency intent. A reference whose Kernel incarnation is not the run's, or an intent with no valid key or digest, refuses as `invalid`. One Kernel envelope then:

- reads the sealed row only once its stored binding names the run's project and job generation, then judges its queue deadline against the completion time;
- requires the caller's target to equal the proposal's, and a memory target to be the live decision at exactly the proposal's object, source revision, and last-change commit token, still served to a local reader of the project;
- requires the live review hold to cover every disclosed input, cited or not, each still live, unpurged, and not `Secret`;
- requires the policy union to be complete (the question template is a member, the members name exactly the disclosed inputs, and their owners are exactly the proposal's ancestry) and every member to stand: the question template at the caller's revision, each descriptor a descriptor row (descriptor kind, current detail version, an identity that re-encodes to itself and names the member, a detail citing the row's evidence) live at its revision and still naming its decision owner, each owner a live decision at its owner revision that a local reader of the project is served, each staged subject this job's sealed row at its digest, and each capture a disclosed MemoryReviewer capture at its digest whose acquisition reference is still ahead of the clock;
- applies the action and records the settlement.

| Action | Canonical effect |
| --- | --- |
| `retire` | The existing decision retirement and its authority cascade |
| `retain`, `no_change` | None: no canonical write, TTL refresh, maturity change, or corroboration |
| `create` | One decision whose id derives from the settlement key, scoped to a live scope that names the run's project, admitted as `ModelInference` with `MemoryClassifierInference` taint under `EventKind::Other` |
| `revise` | A fresh successor with the predecessor's domain and source identity at the next source revision, admitted on its own; the predecessor is superseded |

Create and revise cite each supporting evidence row through a `memory_reviewer_support` decision event, so the support stays cited after the review hold ends. The decision serves no lower than the strictest class its support reads today: when a classification merge later tightens a support row to `secret`, serving withholds the decision. The admission's actual disposition, effective maturity, and visibility are recorded, not the outcome word: a first model-inference admission is a `candidate` with `explicit_labeled` visibility, which explicit search serves and automatic surfaces do not.

The settlement is one receipt under the reserved producer `eidnara-kernel/memory-reviewer-settlement`, keyed by a versioned, length-delimited derivation over the project digest, proposal id, payload digest, generation, and both incarnations. The caller's key is not part of it and the request digest is derived from the key, so an acceptance of a settled proposal under any caller key replays the first settlement, before the review hold, the queue deadline, or the payload is read. A caller key that committed an acceptance replays only that acceptance: its receipt and the settlement share one commit, and the replay answers the settlement receipt. Any other receipt under the key, including one whose result reads as a settlement, conflicts. A key that only received a replay is not recorded. A refused acceptance writes nothing; a store whose live incarnation is not the run's refuses `unavailable` before any replay, and a missing row, a row bound to another project or job, a row of another Kernel incarnation, and a non-proposal row all refuse as one `unavailable` answer before anything else about the row is judged.

### Explicit acceptance over the wire

`review.accept` carries the job's causal identity, the caller's operation key, and the reference and target `review.read` returned. An acceptance binds the proposal its caller read: a request whose reference names another proposal than the completed receipt selects answers `not_selected` before the Kernel is entered, which is what a request built from a retired job's read answers once a later job of the same inputs holds the identity (section 6). The daemon reads the owner's acceptance record, copies the completed receipt (its selection, generation, completion time, and both incarnations) from the Memory Store in the same read as the route's authority and the Memory Store incarnation, checks the record against that incarnation, and releases the store before entering the Kernel, which checks its live incarnation against the record's before it runs the Kernel acceptance above. A refusal reads the live Kernel incarnation, so a record that does not name the live pair answers `disabled` before any other terminal. A create is scoped to the bound project's scope, `project:<digest>`, which a kernel route materializes on its first commit; until one has, a create answers `unavailable`. Any route bound to the project may accept, an observational one included: the owner's record and the connection key are the authority. The caller intent's identity is hex text only: the run's project digest, the job's causal identity, and the SHA-256 digest of the caller's key, so neither a key nor an authority project the Kernel's secret scanner would refuse as an identity can make an acceptance `invalid`; the request digest covers the causal identity and target. The answer is the settlement, or one closed terminal; wire document 7.8 lists them.

### Observational routes

A route bound with harness `cli` is observational. It authorizes and resolves its project exactly as any route does, so `review.list`, `review.read`, and `review.accept` work through it under the existing project authorization, and its session is torn down on close like any other. `host.status` is unaffected: it is a bearer-authenticated channel-0 operation (wire document 7.6) that reads no route binding. It takes no part in background work: the MemoryReviewer worker's project list, the scheduler's root, harness, and schedule selection, and the search maintenance roster read one participating view from which observational bindings are removed before the newest binding on each root is chosen. An observer opened beside a live scheduled harness therefore never replaces that harness's binding, a root bound only by observers contributes nothing, and closing an observer reveals no binding the views were not already reporting. A MODULE-authority project whose only live routes are observational stays dormant: a Ready job waits for a participating route, not for the gate.

`harness` is a claim the client makes on `route.open` and remains scoping metadata; the `cli` value selects observation and grants nothing.

### Exact integers at the client seam

The TypeScript host client decodes a response body exactly when the caller asks for it: `hostStatus` always does, and a routed `request` does under `{ exactIntegers: true }`. Those bodies go through a source-aware reviver (`parseExactJson` in `@eidnara/opencode`'s host client). A safe integer, within plus or minus 2^53 minus 1, stays a plain `number`; any other integer lexeme up to twenty digits becomes a `bigint` carrying its exact value; a longer lexeme, which no 64-bit field can produce, refuses the whole body as invalid JSON. Fractions, exponents, and every other value decode as `JSON.parse` does. If the runtime's `JSON.parse` withholds the lexeme from the reviver, an integer-valued double past the safe range refuses the body rather than passing as exact.

Every other body decodes with plain `JSON.parse`. Module payloads such as the context module's `transform` recipe embed session message values verbatim and are handed back to OpenCode, whose `JSON.stringify` rejects a `bigint`; on that path a model-written integer past 2^53 rounds as it always has instead of refusing the recipe.

Consumers of an exact body apply their field's Rust domain to the decoded value rather than to a rounded double: `exactCount` admits the status counters' unsigned domain through 2^53 inclusive, so `9007199254740992` is accepted and `9007199254740993` is refused instead of rounding into it, and an invalid counter leaves its valid siblings untouched; `exactU64` and `exactI64` cover generations, spans, revisions, commit tokens, and expiries, and return the `bigint` for any in-range value outside the safe integer range. A `number` counts as a wire integer only when it is a safe integer other than `-0`: serde reads `-0` and every decimal or exponent spelling as `f64`, and a double past the safe range may already be rounded (`9007199254740993e0` decodes as 2^53), so such a value is refused rather than presented as exact. Human output prints the exact decimal (`formatExactInteger`); JSON output emits the digits as a raw number token (`rawJsonInteger`), never a string.

`routeOpen(..., { consumerIdentity: null })` omits the ambient `EIDNARA_MODULE_ID` and `EIDNARA_LAUNCH_NONCE` pair for that bind alone; every other caller's bind is unchanged, and no process environment is mutated.

### The review command

`eidnara review list`, `eidnara review show <causal-identity>`, `eidnara review outcome <decision-object-id>`, and `eidnara review status` are the packaged consumers of these reads; `outcome` sends one `review.use_outcome` envelope and renders both counts, or `unavailable` for any answer other than exact counts. Each invocation opens one connection through the installed host client, probes the catalog for the `context` module on that connection, binds one observational route (harness `cli`, session `eidnara-review:<uuid>`, no ambient consumer identity), sends one `review.list` or `review.read` envelope with an explicit `limit` (16 by default, at most 64), or one `review.use_outcome` envelope carrying the decision `object_id` and no limit, and closes; `status` calls `host.status` only and binds no route. Every answer is validated against the protocol vocabulary and the Kernel's byte caps before rendering: a page item outside the outcome or reason vocabulary, a span whose end does not follow its start, text past 32 KiB, an identifier past 512 bytes, or a `terminal` the operation does not define refuses the whole answer as malformed, and no field of a malformed answer is printed. Kernel states such as `invalid:project_mismatch` and `unavailable:store_starting` render as states; management codes such as `route_unbound` and `session_mismatch` render as codes without their messages. Integers keep their exact digits in both text and JSON output.

The status rendering reads the block where `host.status` publishes it, under the `context` component's metrics, and follows the wire document's sanitizer: a block whose state is not `ready` reports every counter unavailable, a counter that is absent, negative, fractional, `null`, or past 2^53 is unavailable rather than zero, a store or activation state the host did not report renders as `unreported` rather than as the wire's `unknown` or `unavailable`, and the counters stay the overlapping populations the sampler reports, with no total or ratio.

## 5. Backup, restore, and mismatch refusal

The Kernel and the Memory Store are two SQLite families that reference each other only by recorded incarnation ids. A MemoryReviewer receipt binds the Kernel incarnation and the Memory Store incarnation it was written under; a Kernel hold binds both; the activation record names both. That is the whole restore contract: the two stores are backed up as one pair and restored as one pair, and every mismatch is refused where it is met.

Both families live under `<data home>/eidnara/context/`: the Memory Store as `store.db` with its `-wal` and `-shm` sidecars, the Kernel as the `kernel/` root holding `kernel.sqlite` and the artifact object store `kernel/artifacts/objects/`. A `.lease` sidecar beside `store.db` records the store's writer epoch; it is not part of a backup, because an open issues its lease above the fence epoch the family itself records.

No operator command performs a Kernel backup or restore in this milestone. `KernelStore::backup` and `KernelStore::restore` exist as library operations on an open store and are what the rehearsal below drives; wrapping them in a command is not in this milestone. The procedure below states what a backup must contain and what a restore is refused for, so that the command, when it exists, and any interim tooling meet the same contract.

Backup:

1. Stop the daemon. The worker is joined before the stores are released, so a stopped daemon has no run in flight. A receipt still `in_progress` at that point is finished by a later pass: the first pass after restart resumes it under the same claim when the same binary reacquires its own slot claim before that claim lapses (`MEMORY_REVIEWER_TASK_LEASE_MS`, 40 s from its acquisition or last renewal; a run renews before an attempt only when more than 250 ms of the lease has elapsed, so the settlement reserve stays at least 9.75 s, and a later round renews while its read batch runs; the worker instance derives from the payload manifest digest); otherwise the claim fences the job until it lapses, and the first pass after that takes the receipt over at the next generation.
2. Kernel database: `KernelStore::backup` publishes a verified copy of `kernel.sqlite` into a private directory (owned by the daemon's user, mode `0700`, not a symlink; anything else is refused as an unsafe destination) and returns its path and the captured commit sequence. This is the only supported Kernel database backup; a file copy of a live Kernel family is not.
3. Kernel artifacts: the database backup carries no artifact bytes. Copy `kernel/artifacts/objects/` beside it. The capture pins the evidence the backup references in the live store, but only for 24 hours unless `capture_pin_expires_at` says otherwise; after the pin lapses, reclamation may remove an object the live database no longer references, and a backup whose evidence names an object the target root does not hold is refused at restore. The objects copy is what makes a backup restorable past that window and into a fresh root.
4. Memory Store: copy the closed `store.db` family (`store.db`, `store.db-wal`, `store.db-shm` when present). The destination must be a directory owned by the daemon's user with mode `0700`, and the copied files must stay `0600`; the store narrows its live family to `0600` on open but nothing guards a copy. The store publishes no backup of its own.
5. Record the pair together with the binary's version and both baseline digests. A backup pair belongs to the binary that wrote it.

Restore of the pair:

1. Stop the daemon.
2. Kernel: place the artifact objects under the target root's `kernel/artifacts/objects/`, open the target root with the same binary that wrote the backup, and call `KernelStore::restore` with the backup path. The restored database keeps its incarnation id, its staged rows, its holds, and its purge tombstones. The restore is refused before anything is displaced when the backup lacks a purge this store committed, or when its live evidence references an object the root does not hold or holds as bytes that fail verification.
3. Memory Store: replace `store.db` and its sidecars with the copied family. It keeps its incarnation id and every receipt.
4. Start the daemon. A proposal selected before the backup reads again through `review.read` while its review hold is live. Neither incarnation changed, so the owner's activation record needs only the new start's credential identity, as after any start.

Mismatch refusal, as the rehearsal test `crates/daemon/tests/memory_reviewer_backup_restore.rs` proves over the data-directory layout above:

| Restored | Beside | What happens |
| --- | --- | --- |
| Kernel database from backup | a root without the referenced artifact objects | `KernelStore::restore` is refused as an invalid restore and the root is left as it was; carrying `kernel/artifacts/objects/` makes the same restore succeed and the evidence readable. |
| Memory Store from backup | a replaced (fresh) Kernel | `review.read` answers `incarnation_mismatch`; resuming the receipt is refused as a binding mismatch; the activation gate closes on `kernel incarnation`. The receipt row stays exactly as backed up. |
| Kernel from backup | a replaced (fresh) Memory Store | No receipt exists, so `review.read` answers `not_selected`; the gate closes on `memory store incarnation`. The Kernel's staged proposal is not served on anyone's say-so. |
| either store | a binary whose compiled versions differ but whose schema baselines match | The gate closes on the compiled version that differs (`identity_mismatch`; the log names the term). Receipts and staged rows are untouched. |
| either store | a binary whose schema baseline differs | The store refuses to open: the Kernel reports `kernel_state: unavailable` with `unavailable_reason: store_unsupported`, and the Memory Store's open fails on its baseline. Neither file is touched, and the activation gate is never evaluated because there is no store to evaluate it against. Nothing migrates a family to another baseline. |

Nothing reconciles a mismatched pair. No migration rewrites incarnation ids, no reset clears receipts, and no code path adopts a staged proposal whose receipt is missing.

Rollback rule: rolling back to an earlier release means the retained old binary together with the backup pair that binary wrote, restored by that binary. A live family the newer release has staged into is not a target for the old binary even when both binaries share a schema baseline: a row shape the old binary does not decode, such as the dependency record in a proposal row's witness (section 4), is refused where it is met rather than migrated. When the release being rolled back changed a schema baseline, the old binary cannot open the current live family to restore into it (the row above), so the live `kernel.sqlite` family and `store.db` family are moved aside first and the old binary restores into the emptied root, with the artifact objects carried as in Restore step 2. If no matching pair exists, the only alternative is an owner-authorized fresh baseline: both stores start empty, the owner writes a new activation record for the new incarnations, and the pending proposals of the abandoned pair are documented as nonportable, because they are bound to incarnations that no longer exist and cannot be carried into the new pair. There is no supported path that keeps one store and replaces the other, except the Memory Store baseline reset below, which keeps the Kernel and leaves its holds and proposals of the old Memory Store incarnation unadoptable.

### History-segment claims column

Appending `claims TEXT NOT NULL DEFAULT '[]'` to `history_segments` changed the Memory Store baseline digest in place. A `store.db` created under the previous baseline refuses to open under this binary, and nothing migrates it: there is no migration, no version ledger, no silent reset, and no change to the Kernel baseline. The reset is one operator step:

1. Stop the daemon.
2. Move the closed Memory Store family aside: `store.db`, `store.db-wal` and `store.db-shm` when present, and the store's `<16 hex digits>.lease` sidecar, all under `<data home>/eidnara/context/`. Leave the `kernel/` root in place.
3. Start the daemon. It creates an empty `store.db` under the new baseline.

The step discards every project's Memory Store state, not only session history: history segments, user memories, notes, capture jobs, and MemoryReviewer receipts. The new store has a new incarnation, so the previous activation record fails closed on `memory store incarnation` and `memstore_baseline_digest` until the deployment owner writes a renewed record naming the new incarnation and digest. Kernel holds and staged proposals bound to the old Memory Store incarnation are refused where they are met, as the "Kernel from backup beside a replaced (fresh) Memory Store" row above describes; no code path adopts them into the new store. Lifecycle reconciliation leaves holds of another store incarnation alone (section 4), so they and their quota charges last until their review expiry.

### Kernel baseline: Batch K1

Batch K1 changes the Kernel baseline digest in place, once per release. Its DDL lands on `main` across several changes and ships as one binary, so a deployment renews its activation record once for the batch. The changes landed so far:

- The `use_outcomes` table and its `use_outcome_decisions` child table, with the `idx_use_outcomes_live_retention` and `idx_use_outcome_decisions_object_fk` indexes and the triggers that keep a serving record's identity and decision set immutable (the record stores its `decision_count`; the decision table accepts rows for it only while its commit is the newest and until that many exist, and only rows naming registry objects of kind `decision` that were live at the record's served commit), set `deleted_at` once, keep `last_transform_at` non-decreasing, retire a record once, and refuse every delete. A serving record holds ids, commit sequences, and timestamps only, is classified `sensitive` and `local_only`, and is retired by the Kernel maintenance slice 30 days after it was recorded unless a committed admission row with a live subject cites it.
- The nullable `use_outcome_id` column on `admission_decisions`, referencing `use_outcomes`, with the partial index `idx_admission_use_outcome_fk`, the `admission_decisions_use_outcome_immutable` trigger, and the `admission_decisions_citation_no_delete` trigger, so an admission row names the record it cites when it is written, the citation never changes, a citing row keeps its subject and commit sequence, and a citing row is never deleted or replaced.
- The nullable `reporter_source_class`, `reporter_taint_class`, and `event_payload` columns on `admission_decisions`. A `mark_disputed` or `contradict` that `kernel.commit` writes stores the reporter's derived classes, the repository reference it cites as JSON in `event_payload`, and in `use_outcome_id` the reporting session's latest serve of the disputed decision before the dispute; every other admission writer stores NULL in the three columns. CHECK constraints hold each class to its vocabulary, set the two classes together, and require `event_payload` to be JSON.
- The `use_outcome_sessions` table, with its immutability and no-delete triggers, and a `session_seq` column on `use_outcomes` and `use_outcome_decisions`. A session's first serve records (project digest, harness, session) once under a compact `session_seq`; each serving record names it through a foreign key over `session_seq` and its identity columns, and each decision row copies its record's `session_seq` and `served_commit_seq`, which the `use_outcome_decisions_written_with_record` trigger checks. `idx_use_outcome_decisions_object_fk` becomes `(object_id, session_seq, served_commit_seq, use_outcome_id)`, so the dispute link above is one seek of the session identity and one seek of that index, whatever the number of serves in the session or of the decision. The session row is classified `sensitive` and `local_only` like the records that cite it.

A `kernel.sqlite` family created under the previous baseline refuses to open under this binary and is left byte-identical: the Kernel reports `kernel_state: unavailable` with `unavailable_reason: store_unsupported`, as the mismatch table above describes, and the activation gate is not evaluated. Nothing migrates it: there is no migration, no version ledger, no silent reset, and no change to the Memory Store baseline. A deployment that keeps the previous family runs without a Kernel. To run with one, stop the daemon, move the closed `kernel/` root aside, and start the daemon, which creates an empty Kernel under the new baseline with a new incarnation. Rows bound to the previous Kernel incarnation, such as MemoryReviewer receipts, holds, and staged proposals, are nonportable and are refused where they are met. The previous activation record then fails closed on `kernel_baseline_digest` and `kernel_incarnation` until the deployment owner writes a renewed record naming the new `kernel_baseline_digest` and the new `kernel_incarnation`.

### Memory Store baseline: Batch M1

Batch M1 changes the Memory Store baseline digest once. Its one change adds the `contradiction_candidates` table, keyed by project digest, descriptor evidence id, and decision object id and holding ids, integers, and times only, with the `idx_contradiction_candidates_decision` and `idx_contradiction_candidates_eviction` indexes, and the `contradiction_candidate_totals` table, which holds each project's candidate row count and bytes. The daemon writes both tables only with `contradiction_candidates.enabled` set. Only the Memory Store writes them, and each candidate write updates the totals row in the transaction that changes the rows. A write from outside the store can leave the totals disagreeing with the rows; the store's only check on a totals row is that it can describe some set of rows (a non-negative count and byte sum, both zero or both non-zero), so after such a write the operator recreates the store with the Memory Store reset in section 5.

### Memory Store baseline: Batch M2

Batch M2 changes the Memory Store baseline digest once. The `memory_reviewer_receipts_no_delete` and `memory_reviewer_attempts_no_delete` triggers keep their names and now guard a receipt that is in progress and the attempts of such a receipt. The other tables, columns, and indexes are the ones Batch M1 left.

A database created under the previous baseline refuses to open under this binary with `StoreError::Baseline` and is left byte-identical; recreate it with the Memory Store reset in section 5. The previous activation record closes the gate on `memstore_baseline_digest` until the deployment owner writes a renewed record naming the new digest and the new store's `memstore_incarnation`. The Kernel baseline is the one Batch K1 left.

## 6. Exposure bounds (Q38)

Provider exposure is bounded by receipts and quotas, not by a spending cap; the daemon holds no billing ledger and none is added.

- One job runs at most `MEMORY_REVIEWER_MAX_ATTEMPTS` (4) attempts, each at most `MEMORY_REVIEWER_MAX_REQUEST_BYTES` (256 KiB) of request body, within `MEMORY_REVIEWER_RUN_DEADLINE_MS` (120 s) less a 10 s settlement reserve. Every attempt is a committed marker in the Memory Store before a byte is sent; a marker that cannot commit sends nothing.
- Every job charges `MEMORY_REVIEWER_RECEIPT_CHARGE_BYTES` (32 KiB) of receipt metadata, and receipt charges plus temporary allowances are bounded per project (64 MiB) and per host (256 MiB). A settled job keeps its rows and its charge for `MEMORY_REVIEWER_SETTLED_RETENTION_MS` (90 days) past its queue deadline; each lifecycle pass then retires up to 256 such jobs (`MemoryStore::retire_settled_memory_reviewer_jobs`), deleting the job, its completed receipt, its attempt markers, and the scan audit its own writes left (its reservation, activation, latest rebind, settle and finish, its ledger writes, and the receipt's copy of the completion's selection; a rebind retires the audit of the rebind it supersedes), and the charge returns to the project. A terminal frozen selection page keeps its 4 KiB charge (`FROZEN_PAGE_RECEIPT_CHARGE_BYTES`) until the same sweep deletes the page, ninety days plus one queue lifetime after its selection deadline and in a pass that retired fewer than 256 jobs, with the scan audit the page still owns: its slot and attempt, the references and continuation cursor of an enqueued page (an expired or failed page released those when it went terminal), and a standalone completion; every job the page enqueued has retired by then. The continuation row (`memory_reviewer_selection_cursors`) stays through every retirement. Its insert and its cursor update each refuse a detected secret, and it holds no scan receipt of its own: an enqueued page's receipt of the cursor retires with the page, and an empty slot's reply receipt retires with its claim, seven days after the claim ends. The quota therefore bounds the review work of one retention window: 2,048 jobs per project and 8,192 per host in any 90 days, less what the window's pages hold. A job enqueued again for a retired job's inputs is a new task under a later `job_id`, and its receipt begins above the highest generation a retired receipt reached (`memory_reviewer_retired_generation`), so the Kernel holds of the second review are its own. A project or host at its quota admits no new job until its pending jobs settle and release room for one, or older jobs retire; a selection under the review switch then queues nothing and the worker logs once per project and process `daemon: memory_reviewer selection queues no new review for a project: the store's review metadata quota refused the reservation (...)`. The sampler reports `receipt_charge_bytes`, `allowance_bytes`, `metadata_quota_bytes`, and `metadata_headroom_bytes` so the host's headroom is read, not inferred, and `projects_at_metadata_quota`, the count of projects whose total leaves less than one job's charge and allowance under the per-project quota; `eidnara review status` prints it, and a value above zero means that many projects are reviewed again only as their pending jobs settle or their oldest jobs retire. The bound is a storage bound: it is what 64 MiB of review metadata holds at the charge of one job, and it says nothing about how many reviews a project needs. What it admits follows from the selection. A review starts when a user message bears on a stored statement, report or note, or any later text bears on work in progress or a note, so demand follows what the user writes and the notes and open work a project holds: a published source reaches at most four memories and an added memory reopens at most four earlier ones. 2,048 reviews in 90 days is 22 a day for each project. A project that passes it keeps the reviews it has, and each selection gives its room to the memories a session receives automatically. A retired job's causal inputs are free again, so a memory with unchanged evidence is reviewed once more at the next selection, about once per window.
- Every job carries at most `MAX_MEMORY_REVIEWER_HOLD_REFERENCES` (512) held evidence references, and a project holds at most `MAX_ACTIVE_MEMORY_REVIEWER_HOLDS_PER_PROJECT` (64) active holds and a host at most `MAX_ACTIVE_MEMORY_REVIEWER_HOLDS_PER_HOST` (256); a run that ends without settling releases its hold rather than leaving it to its cutoff.
- The requested model profile (`model`, `max_tokens`) is what the attempt marker records; the provider's reported model id is checked against the requested one before any text is released, and a reported model that differs ends the attempt as a failed terminal with nothing released.
- A session review (section 2) sends at most four requests a pass, each of at most 24 KiB of encoded messages (at most 512) and 24 KiB of statements with a 4,096-token answer cap and a 90-second wait, one session a pass, and at most three failed attempts that reached the model at one session's newest message within one daemon process, the wait between failures doubling from one minute (`change_detection::MAX_ATTEMPTS`). Its requests commit no attempt marker and charge no receipt or hold; a reported model that differs from the requested one closes review for the process.

Finite cleanup is not evidence of sustainable service. The sampler's per-pass counts say what was swept; the growth of `receipt_charge_bytes` against `metadata_quota_bytes` over time is the measure an operator watches, and section 7 reports what has and has not been measured.

## 9. Attestation verifier

The attestation verifier re-reads repository bytes for a memory decision a model proposed and, when the bytes match, writes a sibling decision of its own, the attestation, that can reach `Verified` without a model call. It runs as one background task per data home beside the MemoryReviewer worker (`crates/daemon/src/verifier_task.rs`), and its pass is `crates/daemon/src/attestation_verifier/bounded_pass.rs`. The records under `docs/properties/attestation-verifier/` state each guarantee below with its check; this section names them by slug.

### 9.1 Reachability and the flag

The verifier is explicit-config-only. It runs only for a project whose effective `verifier.enabled` is `true`, and the shipped default is `false` (`crates/daemon/src/config.rs:279`). With the default, no pass body runs, no repository opens, and no row with `source_kind = "verifier"` is written, so the flag-off guarantee is the default-production behavior (`p6-new-flag-off-nothing-runs`).

`verifier.enabled` is a user-tier key. A project-tier value is ignored with the log line `ignoring /verifier/enabled from project tier; setting is user-tier only`, and both plugins strip it from the project tier before they merge configuration, so a repository cannot turn the verifier on for itself. The pass reads the flag for every bound project before any Kernel read or repository open, so a reload to `false` stops the next pass without a restart.

A pass runs every 30 s while idle and every 5 s after a pass that made progress or failed. Per project per pass it computes at most eight verdicts, reads at most eight times 256 KiB of blob bytes, evaluates at most eight `Active` attestations for applicability, with rows whose standing read fails counted separately, from at most eight pages of 32 verifier decisions, and polls a cooperative 10 s pass deadline before each page, decision, object read, and commit; a read or transaction already under way completes before the pass returns (`p6-new-pass-bounds-and-accounting`). Repository reads happen outside the Kernel writer, so a concurrent `kernel.commit` is not blocked by a stalled read. All cursor, retry, and terminal-reason state is process-local: a restart rescans from the start, and the skips and the receipts of the keyed writes make the rescan write nothing (`p6-new-cursor-never-skips-unresolved`).

The verifiable population is empty at landing. No production decision writer cites `repository_documents` evidence, so with the flag on the verifier counts every current decision under an `unverifiable_` reason until such a producer exists.

### 9.2 Counters

`host.status` carries the counters as `metrics.verifier` on the `context` component; `docs/host-wire-protocol.md` lists every field. They are process-local, start at zero when the daemon starts, and carry no identity, path, digest, oid, or reason text.

The counters split attempts from acknowledged effects. `match` and `mismatch` count verdicts, each of which leads to at most one commit attempt (a verdict whose commit poll finds the pass deadline passed makes none and is computed again by a later pass), and the `unavailable_` and `unverifiable_` buckets count decisions that lead to none; those buckets sum to `considered` at every pass end. `attestation_committed`, `stale_committed`, and `applicability_stale` count only commits the Kernel acknowledged, after the commit returns, and `attestation_replayed` counts a replayed receipt. A commit the Kernel refuses counts under one `commit_refused_` reason or `commit_conflict`. A `commit_refused_io` refusal can follow a durable commit, so the write sets the verdicts committed number at least `attestation_committed` plus `stale_committed` and at most `match` plus `mismatch`; the applicability step's stale marks number at least `applicability_stale`, have no attempt counter, and share the `commit_refused_` and `commit_conflict` fields with the write sets. The next pass resolves such a decision by finding its attestation or its `Stale` disposition. Per-identity checks in the tests, not the totals, are the oracle for exactly one write per decision and oid (`p6-new-pass-bounds-and-accounting`, `p6-new-attestation-identity-unique-per-decision-oid`).

The `metrics.verifier` table in `docs/host-wire-protocol.md` defines which applicability outcome counts in which field. For operations: a refusal one row can cause (an invalid id, a corrupt row, or a malformed field) recurs on every pass, so it resolves the attestation under `applicability_unavailable` with the pass healthy, and a pass with no other progress or failure waits the 30 s idle interval; any other refused read or refused mark marks the pass failed and selects the 5 s retry interval. Each attestation's standing is its own read inside its page's read transaction, so only the refusing row counts `applicability_unavailable`.

### 9.3 What a verifier-authored `Verified` row means

An attestation is a decision under `source_kind = "verifier"` and the classes `(TrustedLocalCode, CurrentCode)` or `(TrustedLocalCode, CurrentConfig)`, admitted to `Verified` through its own `code_present` or `config_present` witness observation. It asserts one thing: the bytes git stores for the cited path in the tree of the commit the model decision's `reachable_from` anchor names hash to the digest of the cited document, up to line-ending normalization. It is witnessed present at a named commit. It is never a statement that the model's summary is true, and it says nothing about the worktree, the index, or any later commit (`p6-new-verdict-deterministic`, `p6-new-attestation-verified-only-via-witness`). The witness detail records the compared evidence id, the digest, the commit oid, the blob id, the path, and the descriptor's object id, lineage, and revision.

The attestation is served at the class the Kernel serves the model decision at, and it cites the compared document evidence through one decision event and the witness detail only, so the `Sensitive` document class does not fold into it through its own rows. A `Verified` attestation is visible on `AutoInject` when that inherited class is `Normal`; a model decision the Kernel serves `Sensitive`, for example through a row-level citation of `Sensitive` evidence, yields an attestation `AutoInject` hides (`p6-new-attestation-classes-and-cited-fields`).

### 9.4 Duplication cost

The Kernel keeps a subject's classes fixed and refuses a cross-party `Replace`, so the verifier cannot promote the model decision in place. The attestation is a new lineage linked to the model decision by a `DerivedReinjection` causality record, and the model decision stays live at `Candidate` with its classes, maturity, and disposition unchanged (`p6-new-attestation-sibling-model-stays-candidate`). Explicit search therefore returns both objects for one finding: the model decision at `Candidate` and the attestation at `Verified`. `AutoInject` returns only the attestation, when its inherited class is `Normal`, because the maturity floor hides the `Candidate`. This is the accepted cost of the sibling design.

### 9.5 Applicability: when an attestation goes stale

After verification resolves or reaches its bound, each pass runs an applicability step over the project's live `Active` attestations, at most eight per pass from a process-local cursor. A cycle pages through the commit its first pass captured, and a page shorter than 32 rows ends it and returns the cursor to the start, so successive passes revisit every attestation in a cycle and an attestation written during a cycle joins the next one. Each pass reads at most eight pages of 32 verifier decisions. A page is one Kernel read transaction whose page statement walks the store's verifier registry entries, those of other projects included, from the cursor through the registry source index, and stops at the first `Active` attestation past the pass's eighth evaluation, so the store's other decisions add no reads and `Stale` attestations cost bounded reads. For a fixed inventory of A `Active` attestations, a republished document is detected within ceil(A/8) passes whose applicability step ends at its evaluation bound, its page bound, or the end of the cycle, plus ceil(R/256) such passes for R live verifier decisions in the project when the page bound ends a pass first (`ProjectRun::applicability` in `crates/daemon/src/attestation_verifier/bounded_pass.rs`). A pass the deadline or a store-wide refusal cuts short advances the cursor only partway. A stale mark the Kernel refuses, or a witness or descriptor read refused for a reason other than the deadline, passes the attestation until the cursor returns to it in the next cycle. A pass whose step ends at a bound with nothing marked reports neither progress nor failure, so the next pass follows the 30 s idle interval. For each attestation the step decodes the witness detail (`crates/daemon/src/attestation_verifier/applicability.rs`) and reads the live `repository_documents` descriptor of the witnessed lineage at the pass snapshot. An evidence digest equal to the witnessed one counts `applicability_current` from the descriptor's registry and evidence rows; a digest that differs is read again with the descriptor row checks, so a row they refuse counts `applicability_unavailable` with no mark. When the checked descriptor carries an `artifact_digest` other than the witnessed one, the step commits one `MarkStale` on the attestation under the classes of its latest admission, with no evidence and a reason naming both digests and the descriptor revision, keyed `(verifier, applicability:<attestation object id>:<descriptor revision>)`. Source capture publishes a new revision when the document's digest changed or the document was recreated after retirement (`p6-document-republishes-only-on-digest-change-and-retires-on-missing`); a new revision that carries the witnessed digest counts `applicability_current`. The attestation leaves `AutoInject` by the `Stale` disposition; the model decision is not touched (`p6-new-attestation-stale-on-byte-change`, `p6-mark-stale-withdraws-support-and-is-terminal-in-place`).

The check is a push from republication, and its limits follow from that:

- A retired document descriptor leaves the attestation `Active`. Source capture retires a document whose file is missing, and a lineage with no live descriptor writes nothing and counts `applicability_unavailable`.
- The step sees only changes source capture published. With source capture disabled, no new descriptor is published, though a descriptor published before it was disabled still marks its attestation `Stale` at the next pass that evaluates it.
- The step compares the witnessed and live digests exactly, with no line-ending conversion, so a republication whose only change is line endings marks the attestation `Stale`.
- A stale mark is terminal for the decision and oid pair. A later revision that restores the witnessed digest leaves the attestation `Stale`, since the step evaluates only `Active` attestations, and the pass writes no second attestation for the model decision and oid, since that attestation id is already registered (`p6-mark-stale-withdraws-support-and-is-terminal-in-place`, `p6-new-attestation-identity-unique-per-decision-oid`).
- The `reachable_from` anchor alone keeps the attestation current: the anchor stays satisfied at descendant commits whatever their bytes, so an attestation's currency rests on the next republication of its document.
- The check runs only while the verifier runs. With `verifier.enabled` off, or between passes, a republished document leaves its attestation `Active` until a pass evaluates it.
- The packing path does not revalidate attestations at serve time; that handoff stays with #657 (OQ6-3).

Alternative 1 of OQ6-4, a digest check kind in the Kernel applicability engine that would judge an attestation against the checkout at read time, is recorded as a handoff to #657, which owns wiring the applicability engine into the packing path. The engine's cheap-check path (`p6-failed-cheap-check-is-stale-and-handed-to-repair`) marks a decision stale from a failed check of its applicability payload; the verifier's step writes its `MarkStale` directly from the descriptor comparison.

### 9.6 Line-ending caveat

The verification comparison accepts the raw blob bytes or one uniform line-ending conversion of them (all LF to CRLF, or all CRLF to LF) whose length equals the cited length. A document whose worktree bytes differ from the blob for any other reason, such as an `ident` attribute, an encoding conversion, or a clean or smudge filter, compares as a `Mismatch` even when the file is unchanged, and the model decision is marked `Stale` (OQ6-8; `p6-new-verdict-deterministic`). The campaign in #1007 measures how often this happens.

### 9.7 Plugin exposure

`source_kind = "verifier"` is outside the plugin route's closed class table, so no plugin can write a decision, an observation, or a disposition under it. The verification page excludes decisions with `source_kind = "verifier"`, so the production pass never classifies or attests its own output; called directly, the classifier also returns `self_source` for a live `Active` verifier decision and `NotInput` for a retired or non-`Active` one, so `unverifiable_self_source` stays zero in production passes (`p6-plugin-source-kind-table-is-closed-and-classes-never-raised`, `p6-new-party-distinct-and-self-refusal`). A plugin can still act on an `Active` attestation in its project scope through its own route: a `disposition` operation (`crates/daemon/src/kernel_routes/commit.rs:790`) with `mark_stale`, `mark_disputed`, `explicit_reject`, `contradict`, or `quarantine` moves it off `Active`, and a `retire_decision` operation (`crates/daemon/src/kernel_routes/commit.rs:1011`) retires it. Each removes the attestation from `AutoInject`; none raises its maturity. This exposure is recorded and not closed (OQ6-15).
