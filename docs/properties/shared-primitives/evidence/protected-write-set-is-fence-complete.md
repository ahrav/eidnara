# `protected-write-set-is-fence-complete`

- **Discovery:** targeted consumer write-surface pass after portfolio evaluation.
- **Primary evidence:** SQLite runs `with_conn` under `PRAGMA query_only`, so an unfenced write fails `SQLITE_READONLY` (`crates/storage/src/lib.rs:125-149`), and `with_conn_unfenced` carries the maintenance statements that guard rejects (`crates/storage/src/lib.rs:151-168`). PostgreSQL exposes enforced read-only and fenced transactions in `with_client_read` and `with_client_fenced` (`primitives@89abb40`) plus an explicitly unfenced autocommit callback, `with_client_unfenced`, for statements a transaction block forbids (`primitives@89abb40`). On SQLite a consumer's schema is one baseline text applied inside the open transaction that claims the fence (`open_sqlite`, `crates/storage/src/lib.rs:565-661`), and any later DDL runs through `with_conn_fenced`, so schema SQL is fenced exactly like DML; the PostgreSQL backend in the source checks the fence in the same transaction as its schema SQL (`primitives@89abb40`).
- **Discriminating fact:** each backend rejects writes on its ordinary callback and retains exactly one named unfenced durable-write surface for statements a transaction block or a read-only guard forbids. Four properties of that binding are not automatic. A callback holding `&Connection` can replace the guard through `Connection::authorizer`, which takes `&self`, so guarded callbacks receive a `GuardedConn` that omits authorizer control, pragma writes, statement batches, and transaction control (`GuardedConn`, `crates/storage/src/lib.rs:219-226`). Enforcement and durability are connection state, not statement state, so `CallbackScope` clears `query_only` even when the read scope unwinds and `pin_fence_durability` re-asserts `synchronous=FULL` before each protected transaction (`crates/storage/src/lib.rs:333-454,548-563`). `query_only` also permits pragma writes, including its own, because a pragma change writes no database content. Enumerating pragma names cannot be complete: `ignore_check_constraints` disables the fence table's constraint, names are case-insensitive, and `ATTACH` and savepoints escape by other means. So `CallbackScope` denies the capability classes instead: every pragma write, transaction control, savepoints, `ATTACH`/`DETACH`, and every non-read action naming the `fence` or `format_marker` tables, for the callback's duration on both the read and the fenced path (`deny_scope_escapes` and `infrastructure_target`, `crates/storage/src/lib.rs:456-546`). Naming only DML would leave the schema route open: a `BEFORE UPDATE` trigger raising `IGNORE` suppresses a later opener's fence claim while that claim still reports success, so triggers, indexes, and table operations on those tables are refused with the DML. `pin_fence_durability` re-asserts `synchronous=FULL` and a WAL journal, since the unrestricted maintenance path can still set either (`crates/storage/src/lib.rs:548-563`). A callback holding the transaction can otherwise send `COMMIT`, after which its remaining statements commit in autocommit. SQLite denies that statement before it executes, so nothing escapes. PostgreSQL has no authorizer, so it verifies after the callback that the transaction is still the checked one, still read-only, and still holding the same lease row (`TransactionWitness` and `require_same_transaction`, `primitives@89abb40`); `SET TRANSACTION READ WRITE` reaches the same state without ending the transaction. That verification reports rather than repairs when the escape autocommitted first, while a mode switch that leaves the transaction open rolls back. Nothing reserves the PostgreSQL lease table against callback SQL either, so the PostgreSQL check also confirms the locked row still carries the epoch the write was fenced against (`primitives@89abb40`). A negative persisted epoch compares older than every positive holder epoch, so both backends reject it rather than let the comparison authorize a superseded writer; PostgreSQL adds the table constraint SQLite already had (`require_nonnegative_epoch` and `ensure_infra_tables`, `primitives@89abb40`).
- **Existing evidence:** the [durable consumer inventory](../durable-consumer-inventory.md) records unfenced durable mutations in the host source's module store that this enforcement fails. `unfenced_connection_rejects_writes` (`crates/storage/src/lib.rs:1663-1686`) and `read_only_callback_rejects_mutation_without_rows` (`primitives@89abb40`) cover read-only rejection; `maintenance_runs_through_the_unfenced_path` (`crates/storage/src/lib.rs:2038-2051`) and `unfenced_callback_runs_statements_a_transaction_forbids` (`primitives@89abb40`) cover the statements a transaction rejects; `a_panicking_read_does_not_strand_the_connection_read_only` (`crates/storage/src/lib.rs:1699-1719`), `a_read_callback_cannot_lower_fence_durability` (`:1721-1787`), and `a_read_callback_cannot_clear_the_read_only_guard` (`:1789-1837`) cover the read scope; `a_callback_cannot_end_the_fence_checked_transaction` (`:1839-1884`) denies the transaction escape on SQLite while `a_callback_that_ends_the_transaction_is_rejected` (`primitives@89abb40`) and `a_read_callback_cannot_escape_read_only_mode` (`primitives@89abb40`). Both PostgreSQL escape checks ran only when the callback returned `Ok`, so a callback that escaped, wrote, and then failed propagated its own error while the unfenced write survived; `a_failing_callback_cannot_hide_an_escape` (`primitives@89abb40`) covers the read, fenced, and schema paths of that backend, and `a_failing_callback_that_stays_inside_reports_its_own_error` (`primitives@89abb40`) holds the line that an aborted transaction still reports the callback's own diagnosis rather than `current transaction is aborted` report it on PostgreSQL; `a_negative_epoch_fails_closed` (`primitives@89abb40`) and `a_regressed_positive_epoch_fails_closed` (`primitives@89abb40`) fail closed on an unreconcilable epoch; and `a_callback_cannot_damage_the_lease_row_it_is_fenced_against` (`primitives@89abb40`) with `a_suppressed_epoch_increment_is_rejected` (`primitives@89abb40`) and `open_verifies_the_stored_epoch_matches_the_issued_one` (`primitives@89abb40`) protect the lease row, while `a_callback_cannot_damage_the_fence_row_it_is_checked_against` (`crates/storage/src/lib.rs:1886-1978`) does the same for the SQLite fence and format-marker rows, and `a_fenced_callback_cannot_rewrite_the_format_marker` (`crates/storage/src/lib.rs:1980-2036`) refuses an update of, or a rename onto, the marker row. None covers consumer completeness.
- **Failure scenario:** domain code performs a protected durable mutation through a named unfenced closure, reroutes a rejected `with_conn` write to `with_conn_unfenced`, ends the checked transaction and opens a replacement so its writes commit under no verified fence, or operates against a lease row whose epoch was corrupted before the non-negative constraint existed.
- **Timing window:** stale connection after handover.
- **Instrumentation:** authoritative inventory of durable-write sites plus at least one authoritative fence check atomically bound to each protected commit.
- **Uncovered PostgreSQL escape:** a callback can run `pg_advisory_unlock_all` and release this session's lease, after which a second `open_postgres` acquires the same key while this store is live and both can reach the unfenced maintenance surface. A check for the lock was added and then reverted: `pg_locks` does not distinguish a session-level advisory lock from a transaction-level one, so a callback taking `pg_advisory_xact_lock` and releasing the session lock satisfied the check while leaving no lock after commit. A check that passes without the invariant is worse than none, because the catalog would then claim coverage.
- **Convergence note:** the PostgreSQL side received six successive validations in one review, each placed after the statement the previous one missed, and the last two were defeated by deferred constraint triggers firing at `COMMIT` and by the store's own version-record insert running after the lease-row check. That is evidence that validation is the wrong instrument on this backend, not that a further position exists; SQLite closed the same class by removing the capability instead.
- **Open-question log:** an authoritative protected write-set classification remains unavailable, and moving the SQLite consumers' unfenced mutations onto the fenced APIs is a required upgrade rather than a deferred one. Whether maintenance statements through `with_conn_unfenced` and `with_client_unfenced` count as protected writes needs the same owner, as does whether the fenced callbacks should receive a capability-narrowed handle instead of one that can execute arbitrary SQL; detection cannot see a callback that opens a replacement transaction.
