## Failure scenario

Bytes changed at the cited path, source capture published a new descriptor revision with the new digest, and the attestation is still `Active` after a pass evaluated it; or a second `MarkStale` for one revision.

## Timing windows and dependencies

Between the applicability read and the commit, the attestation can be retired, re-disposed, or superseded, and the lineage can be republished again or retired; the envelope recheck turns a re-disposition to `Stale` into `Skipped(AlreadyStale)`, counted in no field with the pass healthy, and each other change into `Changed`, both with no write; a restore since the page's reads also makes the mark `Changed`, and the step stops the project after that one refusal. A commit refused with `Io` can follow a durable commit: the next evaluation finds the attestation `Stale` and passes over it, and a direct retry replays the key's receipt. The step depends on `p6-document-republishes-only-on-digest-change-and-retires-on-missing` for the live descriptor's digest; a new revision can carry the witnessed bytes, as for a recreated document, so the step stales only on a digest other than the witnessed one, and it never sees a change source capture did not publish.

### Q: Which mechanism carries applicability?

- Sources examined: OQ6-4 and its resolution in [#1174](https://github.com/ahrav/eidnara/issues/1174).
- Findings: The owner chose alternative 3, the push model inside the pass. Alternative 1, a digest check kind in the Kernel applicability engine, is a handoff to #657, which owns the packing-path wiring of that engine.
- Missing evidence: none.
- Conclusion: resolved with answer.

### Q: What leaves an attestation `Active` although its bytes changed?

- Sources examined: `evaluate`, the trigger scope in [#1174](https://github.com/ahrav/eidnara/issues/1174).
- Findings: a retired descriptor or a lineage with no live descriptor writes nothing, because absence also follows from disabled source capture; with source capture disabled nothing is republished; the `reachable_from` anchor alone stays satisfied at descendant commits; and the step runs only while the verifier is enabled. The limitation is documented in `docs/memory-reviewer-operations.md` section 9.5.
- Missing evidence: none.
- Conclusion: resolved with answer.

### Q: How does the step progress under N without a cursor table?

- Sources examined: `ProjectRun::applicability`.
- Findings: the cursor is a process-local registry `(source_id, object_id)` pair per project; it passes an attestation once it is evaluated or passed over, stays before an attestation the deadline cut, and returns to the start when a page is shorter than `PAGE_ROWS`; each cycle pages through the commit its first pass captured, so it reaches its end while attestations keep arriving, and each live `Active` attestation is evaluated once per cycle of passes. A restart or a store incarnation change starts the cycle over; a `Stale` attestation is passed over and a repeated stale mark replays its key, so a rescan writes nothing new.
- Missing evidence: none.
- Conclusion: resolved with answer.
