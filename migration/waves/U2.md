29 lease records converted to the METHOD field order, 17 records discovered at

`lease-store-density.md`). Evidence paths point at destination files with line
ranges derived from this tree. PostgreSQL citations name the source repository
and commit with no path.

Two byte-stable fixtures are authored here:
`crates/cache-stability/tests/golden/cache-stability-golden-vectors.json` and
`crates/storage-types/tests/golden/storage_vectors.json`. The second is the

## Adapted beyond renames

- `cache-stability`: module doc, one test message, a nested `if let` in
  `step_soft` collapsed into a let chain.
- `lease`: first doc line, `fnv1a` doc, six malformed-epoch cases,
  `LeaseKey::identity` rejects the `U+001F` separator, appended tests.
- `storage-types`: module docs, `Debug` redacts the DSN, `sqlite_store_path`
  rejects path components in `module_id`, appended tests.
- `storage`: one-baseline `open_sqlite(descriptor, baseline)` with an
  identity gate and `StoreError::Baseline`; `fence` and `format_marker` as the
  infrastructure tables; public re-exports of `GuardedConn`,
  `MaintenanceConn`, `SchemaObject`, `schema_inventory`, `APPLICATION_ID`, and
  `USER_VERSION`. A pristine file receives the whole baseline text once with
  `PRAGMA application_id = 0x4549444e` (`EIDN`), `PRAGMA user_version = 1`,
  and one `format_marker` row holding the SHA-256 of the text. Any other file
  must present exactly that identity or the open is refused before any pragma
  or transaction. No file is upgraded, adopted, or repaired, and no version
  ledger exists. `fixtures/schema/storage-inventory-v1.json` is the fresh-file
  inventory; `cargo run -p storage --example schema-inventory` reproduces it.
- Crate manifests: crate names, `publish` and `rust-version` inherited from
  the workspace, workspace dependency pins, descriptions without product
  branding.
- `docs/properties/METHOD.md`: the record template and the U1 test fixture
  use a spaced hyphen (`yes - <note>`) where they used an em dash.

## Dropped

- The PostgreSQL backend. Records that cited its checks keep the SQLite half;
  its tests stay listed in `existing-checks.md` as source provenance only.
- The source's schema-migration machinery. The store opens against one
  baseline text and refuses anything else.
- The source's three-OS CI matrix, live PostgreSQL job, push-seal version
  gate, and release tag resolver. The genesis release ships
  `linux-x64-gnu` only, and every crate here is `publish = false`.
- The wave's control records (property-impact, architecture-impact, waivers,
  receipt) and the generated property index. See the U1 note.

## Architecture review

Pre-port and post-integration runs of the architecture review carried the
same four candidates:

- C1, Retire the PostgreSQL backend variation: Worth exploring, recorded.
  `postgres_database_name` has no consumer in this workspace; retiring it is
  a contract change that must replace the `storage-types` golden-vector
  fixture.
- C2, Single FNV-1a implementation: Speculative, recorded. The
  `storage-types` copy exists only for `postgres_database_name`, so C1
  removes it.
- C3, Merge `GuardedConn` and `MaintenanceConn` forwarding: Speculative,
  rejected. The two structs are the capability boundary between read
  callbacks and maintenance; a shared handle would leak batch and pragma
  access.
- C4, Remove the migration runner: Strong, accepted. A store has one schema,
  so the runner, the `Migration` type, and the version ledger were surface
  without a second implementation. The one-baseline `open_sqlite` above is
  the result.

The post-integration run accepted no further structural change.
